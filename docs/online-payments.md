# 在线支付协议与运行手册

本阶段为每个独立部署实例提供在线订单支付。当前没有多租户、钱包付款、充值、余额组合付款或真实退款执行。

## 已核实的服务商协议

当前实现的协议配置为 `zpay_epay_v1`，对应 ZPAY 官方公开的易支付兼容 API。它不代表所有名为“易支付”的服务商或克隆协议。

| 能力 | 协议及处理 |
| --- | --- |
| 创建支付 | `POST https://zpayz.cn/mapi.php`，`multipart/form-data`；使用 `type=alipay` 或 `type=wxpay`；金额单位为人民币元，最多两位小数。成功响应的 `code=1`，适配器读取 `trade_no` 和 `qrcode`、`payurl` 或 `payurl2`。 |
| 二维码/跳转 | `qrcode` 是二维码内容，前台在本地渲染二维码；`payurl`/`payurl2` 只接受 HTTPS 跳转链接。 |
| 异步回调 | GET 回调；仅 `TRADE_SUCCESS` 被视为成功候选。先校验官方 MD5 签名和商户号，并在发起网络查单前持久化原始回调事件；随后用商户凭据通过 HTTPS 查单。回调参数中的订单号、交易号、方式、金额与查单不同会建立待核对案例。 |
| 主动查单 | `GET https://zpayz.cn/api.php?act=order`，以 `pid`、`key` 和商户订单号查询；必须确认返回的 `pid`、`out_trade_no`、`trade_no`、`type`、`money` 和 `status`。仅 `status=1` 表示已支付。 |
| 配置测试 | `GET https://zpayz.cn/api.php?act=balance`；仅用于商户凭据可用性检测，不发起真实支付，也不读取或显示余额。 |

ZPAY 文档规定签名字段按参数名 ASCII 升序，排除 `sign`、`sign_type` 和空值；参数值不做 URL 编码；将键值串与商户密钥拼接后计算小写 MD5。回调可能重复发送，服务商要求返回 `success`，并要求商户验证签名和金额。[ZPAY 官方开发文档](https://api.zpayz.cn/doc.html)

已启用的支付方式为支付宝和微信。它们是一个通道中的支付方式，不是两个固定服务商。当前服务商只支持顾客扫码或访问服务商支付链接；没有实现支付宝/微信官方直连接口、JSAPI 或小程序支付。

未指定具体码支付服务商，因此 `codepay_unconfigured` 只是不可启用的占位项。协议确认前不会尝试推测签名、参数、金额单位、回调或查单规则。ZPAY 文档没有为本接入提供可验证的沙箱收款接口；正式商户凭据下的真实端到端收款仍是 `NOT_VERIFIED`。

## 支付与入账状态

1. 顾客请求创建支付时，API 从已封存订单计算人民币应付金额，锁定订单，验证所有权、待付款状态、订单截止时间、通道状态和方式，并为外部支付尝试写入未来截止时间。数据库事务提交后才调用服务商。
2. 新支付尝试从 `created` 开始。服务商明确拒绝时才标记 `failed`；成功响应经过数据库保护后转为 `pending`。超时、非 JSON、身份缺失或无法确认的响应保持待确认，不会以网络异常判定失败，也不会自动创建第二个服务商订单。
3. 同一订单的活动尝试会被复用。订单级幂等键防止同一请求重复创建；订单行锁串行化多个服务实例的付款点击。
4. 回调、主动查单、重复查单和异常恢复都进入同一结算事务。签名有效的已付款回调先持久化，认证查单确认的实际交易号、支付方式和金额写入不可变事件；只要商户订单归属、商户身份、币种和正数金额可确认，服务商查单报告的实收金额就会保存为 `payment_receipts`，即使回调字段与之矛盾。
5. “服务商确认有资金”与“资金可推进订单”是两种状态。存在待核对案例时，实际回执保留在财务凭证中，但支付尝试不能转为可履约的 `succeeded`，订单不能因该回执进入 `processing`。只有没有开放案例且足额、按订单期限收到的回执才由现有受保护触发器推进订单。
6. 顾客返回支付页或手动刷新只会读取或发起限频查单。后续一致的查单会补齐首次遗漏的回执，但不会自动消除已有冲突案例。

网络请求不持有数据库事务或订单行锁。入账遵循“订单行 → 支付尝试 → 服务商交易号事务锁 → 回执”的锁顺序；同一交易号由 PostgreSQL advisory lock 串行化，保护多实例并发回调和查单。支付尝试插入与状态转换仍受④-5数据库保护；订单关闭路径不会反向更新支付尝试。

数据库关闭保护谓词同时检查开放核对案例和“已验签、已付款、尚无回执”的回调事件。这样回调等待查单期间，超时worker和顾客取消都不能先关闭订单并释放库存。若查单证明是普通足额按时收款，写入回执后这一临时保护自然由回执取代；若查单与回调冲突，开放案例继续保护订单和库存。购买限额继续按④-6的订单事实计算，开放案例不会删除或重算订单历史。

## 异常款项与恢复

| 情况 | 处理 |
| --- | --- |
| 无效签名或篡改回调 | 保存必要的未验证事件，拒绝回调，不写回执、不推进订单。 |
| 重复成功通知 | 已处理通知幂等确认；不会重复写回执或重复履约。尚待确认的事件按服务商策略安全重试。 |
| 服务商创建请求超时或响应未知 | 保留 `created`/未知状态；同一订单复用原尝试并经查单确认，不宣称付款链接可用或服务商创建失败。若服务商订单已创建但没有可恢复的支付链接，后台可见待核对证据，不能安全地另造服务商单。 |
| 查单身份或响应无法确认 | 保留未知结果，不写资金回执，不标记失败。顾客手动刷新和回调会受 10 秒查单冷却约束，API 另有速率限制。 |
| 少付或超付 | 保存服务商确认的实际金额和支付尝试；按④-1回执触发器规则标记 `amount_mismatch` 或累计 `excess`。当前尝试收到的金额与应付金额不符时记录为 `amount_mismatch`，支付状态需要核对，订单不会进入 `processing`。 |
| 同一服务商交易号已关联其他尝试 | 不写第二张回执；把已认证的查单金额及交易号保留在服务商事件和开放案例中，阻止该订单关闭或履约。 |
| 订单已关闭或付款迟到 | 保留实际回执；支付尝试标记 `late_succeeded`，订单不重新打开，也不自动履约。数据库按订单/支付截止保护分类，服务商 `endtime` 原文作为事件证据保留，不因未声明时区而覆盖数据库收款事实。 |
| 签名回调与认证查单的金额、交易号、支付方式或身份冲突 | 保存两份原始事件和查单确认的实际金额回执，建立不可变的开放核对案例；订单不能正常结算，库存不释放，顾客后续查单不能绕过案例。 |
| 少额、超额、迟到或金额不符回执 | 保留回执及实际金额。金额不符/超额不能正常履约；超时关闭规则也不能丢弃未退款收款。迟到回执沿用④-1分类，不会重新打开已关闭订单。 |
| 认证查单无法确认或与当前尝试身份不符 | 只保留查单事件，不把未知响应当作资金回执。若此前有已验签的付款回调则建立开放案例并保护订单；否则留待后续安全查单。 |

后台订单详情展示每个核对案例的开放/解决状态。管理员可执行“重新向服务商核验”，这会发起新的认证查单，不提供手工标记付款入口。只有结果与历史认证查单和现有实收回执一致、且交易号没有其他尝试冲突时，数据库才记录解决管理员、时间、查单摘要、交易号、支付方式和金额。足额按时回执随后通过支付状态保护转为成功并推进仍待付款的订单；迟到回执只会完成核对，不会恢复订单。金额不符、超额收款和仍存在交易号冲突的案例不会由该操作强行解决。

退款边界：本阶段不执行真实退款。开放案例中的实收款项保持在回执及核对事件中，不会自动抵扣订单、履约或从历史中删除；已有④-1退款分配和订单关闭保护仍阻止丢弃未退资金。金额不符、超额以及跨订单交易号冲突需要服务商侧核实及后续退款/对账能力，本阶段不伪造完成状态。

后台订单详情可查看通道、支付方式、服务商订单号/交易号、创建与完成时间、实收回执、事件验证状态和错误代码。管理员不能用按钮伪造付款。

## 商户密钥配置与轮换

每个独立部署实例使用自己的加密密钥环。API 只接受环境变量 `PAYMENT_CREDENTIAL_KEY_RING`，格式为单行 JSON：

```json
{"activeKeyId":"v1","keys":{"v1":"BASE64_OF_32_RANDOM_BYTES"}}
```

通过 `openssl rand -base64 32` 生成 32 字节 AES 密钥。仅将环境配置交给 API 运行环境；不要提交到 Git、浏览器配置、SSR 状态、管理列表或日志。商户号与商户密钥用 AES-256-GCM 加密存入数据库；管理员表单保存后不会回显明文。密钥为空的通道更新只保留现值。每次通道配置变化写入不可变审计记录。

轮换步骤：

1. 在所有 API 实例环境中同时配置新旧密钥，令新密钥成为 `activeKeyId`，并保留旧密钥供历史数据解密。
2. 以管理员访问“支付通道”页面，运行“用活动密钥重新加密历史凭据”。API 会重加密通道配置并为每笔历史支付尝试追加新的凭据封装版本，保留原尝试所关联的商户凭据版本；操作写入审计。
3. 检查返回的重加密数量和后台审计记录。完成后从所有实例环境中移除旧加密密钥，再重启 API。

不要在没有先部署新旧密钥环的情况下切换活动密钥。若旧密钥仍被数据库中的任一通道或支付尝试使用，移除后将无法验证相关历史回调或查单。

## 测试边界

自动化测试通过本机回环 HTTP 服务商夹具运行真实 HTTP 请求，并使用真实 PostgreSQL 事务、触发器和唯一约束。夹具只在测试环境显式启用；`createApp` 只允许 `NODE_ENV=test` 下的回环 HTTP 覆盖地址。测试夹具不能被生产 API 配置成服务商。

本地与 CI 的支付集成测试需要专用 `_test` PostgreSQL 数据库。它们会重建该测试库的 `public` schema；不得把生产库或共享数据目录配置为测试库。浏览器测试通过本机夹具，不代表服务商真实收款已经验收。
