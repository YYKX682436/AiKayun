# ⑥-2B 购买行、统一报价与不可变成交资料

## 基线与范围

实施基线为 `3ab2af9dd659c7fef317e755ab9ffe0fbd3c9c18`。本阶段只扩展现有购物车、报价、订单项、库存预留、购买限制和私有附件体系。⑥-2A及 R1/R2/R3 的冻结模板、草稿和后台准备功能不重做；商品/SKU 的准备关联本身不使旧购买入口要求填写。正式填写、上传、附件展示和正式启用入口在⑥-2C。此阶段不发起供应商采购、不改 `http_json_v1` 请求、不建立采购价格或第二套订单/履约状态机、不部署生产。

## 身份与契约

- `lineId` 是购买行的稳定 UUID。服务端购物车行拥有持久 `lineId`；立即购买和本地游客行的请求行 UUID 由浏览器生成，但只用来定位与恢复，不作为资料真实性证明。订单项保存来源 `lineId`，逐单位履约仍以订单项 UUID 和 `unitIndex` 定位。
- 内容身份由服务端对 SKU UUID、冻结模板版本 UUID、规范化版本和规范化有效值的规范 JSON 求 SHA-256。复用⑥-2A 规范化：保留前导零、大小写、有意义空白；图片仅用稳定附件 UUID。`draftId` 可定位私有草稿，不能参与内容相等判断。无资料行使用明确的 `templateVersionId: null, normalizationVersion: null, values: null`；有模板但有效可选值为空仍有模板 UUID 和规范化版本，因此与无模板行不同。客户端摘要不可信。
- 购物车唯一键为 `(customer_id, sku_id, content_identity)`，三列均非 NULL；迁移把旧行映射成无资料身份，保留数量、时间、归属和已删 SKU 的不可用显示，SKU 不新增外键。全车最多 50 行，同 SKU 跨行数量合计最多 99。相同内容合并数量，异内容分行；容量或数量失败时整笔事务回滚。
- 未带版本的旧报价、下单、购物车合并请求继续使用旧 SKU/数量规范化及旧摘要算法。新请求显式 `version: 2`，每行带 `lineId, skuId, quantity` 与可选的 `draftId, draftRevision`；不能从请求中接受内容摘要或金额。请求恢复指纹只从原请求材料计算，包括版本、稳定行/草稿引用、指定修订、SKU、数量；不重新读取当前草稿。历史 `orders.request_sha256` 不改值，并按请求版本选算法。旧 pending batch 保持原 owner、mergeId、请求体和摘要。
- 新行级修改/删除使用独立路径并按 `lineId` 定位；旧 SKU 路径只作用于无资料行。立即购买可直接新报价和下单，不强制写购物车。所有入口最终调用同一购买资格与报价逻辑；⑥-2C 正式启用时在该逻辑引入必填门禁，旧格式不能成为绕过路径。
- v2 报价按内容折叠游客的同内容行时返回 `sourceLineIds`。浏览器只在原本地快照和 Web Lock 仍匹配时将来源行折叠到保留 `lineId`，映射勾选目标并重新报价；不会自行解密或把 `draftId` 当作内容身份。游客 v3 存储仅保存行/草稿引用及未决原请求；旧 v2 购物车的未认领行在明确进入结算前、同一 Web Lock 下升级成稳定行，已认领 pending batch 的 owner、mergeId、items 原文不变。v2 未决订单使用固定 localStorage 键保存原 key、quoteToken、行/草稿引用和修订，绑定真实顾客 UUID 或游客 session UUID；Web Lock 与原始快照检查保护跨标签写入。订单确认后同一条记录变成仅含 owner、选择指纹、原 key 和 orderId 的完成回执。未知结果同内容继续复用原 key；旧结算 URL 以原 selectionId 只找回旧订单，而顾客从购物车明确再次结算会获得新 selectionId 并可正常复购。跨主体仅未决请求及原链接被隔离；已知 409 的终态不会永久挡住另一主体的新选择。旧 sessionStorage v2 未决请求先原样迁入共享存储，旧 v1 请求格式不改。
- 前向迁移为 `storefront_customer_policy` 增加 `purchase_forms_enabled BOOLEAN NOT NULL DEFAULT false`。既有策略行在升级后仍为 `false`；⑥-2B 不提供管理员或顾客启用入口。统一报价资格读取此明确开关，⑥-2C 才接入正式启用操作，准备关联本身不切换开关。

## 草稿、编辑与游客认领

- 把草稿保存、完整性校验及指定认领抽取为可在调用方事务内执行的原语，旧 API 仍以薄事务包装。行绑定记录 `draftId + draftRevision + templateVersionId + normalizationVersion + contentIdentity`；一份草稿不能同时绑定两个不同购物车行，跨 SKU 复用须另存草稿。绑定草稿的普通独立保存、续期、删除、附件改动必须被协调门禁阻止，或把旧绑定明确判失效；绝不使购物车身份与正文静默分离。
- 正常行编辑在同一事务锁主体、行、草稿及附件，校验 expected 行/草稿修订，更新草稿和行身份。碰撞时把数量原子加到已有内容行，删除源行，返回保留的 `lineId`；不修改其他行的草稿。超出 50 行或同 SKU 99 件时，原行与草稿都保持原样。
- 顾客合并游客批次：先对当前顾客取 UPDATE 锁并验证会话，再锁幂等记录；已完成则直接返回原结果。首次请求才验证原游客会话，并按稳定顺序锁指定草稿、检查归属/期限/容量、单向认领，再合并购物车和写结果，全部在一个事务内。不得扫描或认领未指定草稿；失败不留半认领。避免先对游客会话取 SHARE 后再升级为 UPDATE。

## 报价、下单与锁顺序

- v2 报价从已认证的顾客或游客主体读取指定修订草稿，校验所有权、活动状态、期限、冻结模板版本、完整性和 ready 附件。服务端计算内容身份；同 SKU 跨行汇总库存、SKU 限购，商品限购汇总该商品全部行。报价 token 包含每行实际内容身份、模板/规范化版本、草稿修订、准备关联版本与既有价格、库存、资格信息。准备关联目前不自动启用旧入口，但显式 v2 草稿必须与其指定准备版本一致。任何这些事实变化都要求重新报价。
- 创建订单先认证当前主体并锁幂等键查已提交订单；命中且原请求指纹相同就返回原订单，不再要求源草稿仍有效。首次执行才准备附件归档。正式下单事务再次按同样锁序读取并校验草稿和附件、重算报价；预报价不构成成交授权。游客批次合并已完成后的同顾客重放，也先查该顾客幂等记录，不再检查原游客会话。
- 统一顺序：顾客主体 UPDATE → 顾客会话 SHARE → 请求幂等锁/记录；游客首次请求则原游客会话 UPDATE；其后目录商品 UUID SHARE → SKU UUID UPDATE → 库存行 UPDATE → 履约配置 SHARE → 指定草稿 UUID UPDATE/SHARE → 附件 UUID SHARE → 已准备归档对象；订单插入后按订单项和预留既有顺序写入。草稿操作自身也先锁主体再锁草稿/附件。多行 SKU/商品先去重并排序；`40001`/`40P01` 保留有界重试。不得在锁中复制文件或调用外部 HTTP。

## 成交快照、封单与附件

- 新订单项在创建事务内固定来源行、模板版本、规范化版本、内容身份、独立加密的规范化填写值、稳定附件清单、对象 UUID 和 SHA-256。无资料新行也记录明确的无资料状态；旧订单保持真实的历史无本阶段资料状态，不能按现行模板补填。订单资料使用既有密钥环派生独立用途密钥，AAD 绑定订单项 UUID；不能把以草稿 UUID 为 AAD 的密文直接搬来。缺失历史密钥时明确报错，不用空值替换。
- 数据库在 `items_sealed` 转换时检查新订单项资料完整；封单后拒绝 INSERT 补造、UPDATE、DELETE 和 TRUNCATE。解除订单项同单 SKU 唯一约束后，限购 SQL 按 `(product_id, product_variant_id)` 汇总当前订单全部行，再检查每单、累计与 24 小时。原商品级口径、历史订单是否占额及库存事件、退款、关闭、履约保护保持不变。
- 数据库封单门禁还核对无资料快照的 SHA-256 与订单项 SKU 所对应的规范 JSON；有资料快照的加密正文无法由 SQL 自行解密重算，由交易服务在锁内重新验证并生成。归档对象只能以 `prepared` 状态插入，存储路径必须与对象 UUID 精确对应，防止直接 SQL 伪造不可清理的 `retained` 对象。
- 图片在现有私有卷的独立订单资料命名空间归档。事务外完成源文件 SHA-256 校验、复制、fsync、不可覆盖发布及 prepared 元数据持久化；订单事务仅锁定并绑定已校验对象与订单项引用。未绑定 prepared 对象过宽限期才可清理；结果未知先按订单/引用核对，清理竞争取得对象锁并重查引用。草稿修改、删除或到期不删除已成交归档；旧私有交付文件和草稿清理器不得扫描订单资料目录。授权读取按订单归属和持久快照，不回读草稿；正式顾客 HTTP 展示留给⑥-2C。

## ⑥-2B R1 精准复审

R1 固定审查基线为 `e928b65ddbd668f3f0d7da3175faba7fb4d74de7`，开始时本地 HEAD、origin/main、远端 Git main 与 GitHub main 一致且工作树干净。本轮只修复游客主体绑定竞争、拒绝报价重试丢失关联链接、成交快照与有序附件清单的数据库约束；继续停在⑥-2B。

根因与修复边界：

1. 游客会话在订单提交锁之外建立，两个无 Cookie 标签能分别取得不同会话，迟到的 Set-Cookie 可能使本地 pending owner 与实际订单主体不同。顾客身份探针把两者都看作 customerId=null。本轮统一协调所有现有游客会话建立入口和订单提交，并由服务端校验浏览器预期的游客主体。已有 pending 的 owner、key 和原请求材料不改绑，旧请求摘要算法保持。
2. `rejected` 重试创建新 pending 时只保存当前 selectionId，丢失原主链接及 aliases。本轮在同一存储锁内保留、去重并限额检查整个链接集合；完成回执读取当前持久集合，使主链接及任一别名都恢复同一次操作。顾客明确从购物车建立新选择时仍可复购。
3. 原快照 CHECK 与封单比较使用 nullable 表达式，缺失规范化版本或数组越界可产生 NULL 而未被拒绝。本轮以新增前向迁移检查既有异常并明确失败，收紧非空受支持版本、数组维度/下界和来源身份与序号的完整有序配对。原迁移与已封存交易不重写。
