# ⑥-4B-1：采购来源冻结与持久身份基础

## 范围与边界

固定基线为 `6794ffd3a7160cab08bce53e35c2eec99e84cf9c`。开始时本地 HEAD、`origin/main`、GitHub `main` 一致；基线 Actions `40478668068` 已完成且成功。本阶段只建立成交来源、操作和本地单位身份及资格判断，不实现供应商采购、查单、退款、HTTP 适配器、采购 worker、上游数量、请求体或预算账本。原 `http_json_v1` 能力声明和幂等规则不变，卡易信只读 API 和数据库禁售门禁保留。

当前没有真实合格采购来源。生产 `selectCheckoutProcurementSources()` 固定返回空数组，没有环境变量、SQL 配置、管理入口或顾客入口可以把 reviewed 映射变为采购来源。专项测试在测试进程通过模块替身返回合成选择；该替身不注入生产构造或配置。数据库存储关系自身不会启动采购或改变现有商品的六种履约方式。源快照存在与付款后能否准备是不同问题，二者均不证明可以向上游采购。

## 持久关系与成交冻结

- `order_item_procurement_sources` 对每个订单项最多保存一行，以订单、订单项、商品及 SKU UUID 确定本地身份。它限制性引用原 `order_item_purchase_snapshots`、审核 `supplier_product_mapping_versions`、供应商配置版本和凭据版本。行内冻结模板版本/摘要、规范化版本、成交内容身份、规则摘要、结构指纹以及上游商品 ID、SKU 类型、编码和规格组合。映射完整规则和结构从不可变审核版本读取；历史配置版本指向同一连接的凭据版本，凭据重包只更换密文封装，不更换其历史身份。历史解密仍需要部署方保留原密钥环。
- 成交资料正文继续只存在于原订单项专用加密快照；图片通过相同订单项关联原 `order_item_purchase_attachments` 与保留的私有归档对象。采购来源不复制正文、密钥、草稿或图片字节，也不提供新的附件访问路径。`content_identity` 是现有规范化购买行内容身份，不是可逆正文或上游采购参数。
- 源选择只能发生在原下单事务的幂等查询之后、订单项及原资料快照建立之后、订单封存之前。新来源插入触发器锁定并核实父订单尚未封存，订单项与资料快照、当前 reviewed 映射版本、供应商当前配置、历史凭据、模板、摘要和上游身份必须一致；直接 SQL 的跨订单、跨 SKU、错误映射/凭据及封存后补绑被拒绝。来源版本失效返回 `409 CHECKOUT_SOURCE_CHANGED`；所有来源和原订单在同一事务提交或回滚。
- 已有幂等键先读取历史订单，不运行来源选择；无来源的历史订单不会因为新映射而补绑。SKU 相同但资料不同的购买行保留不同订单项；规范化内容相同的行沿用现有合并规则。采购单位的身份是订单项 UUID 加从 1 开始的 `unit_index`，不是名称、展示标签或数组位置。

## 操作与分配

`procurement_operations` 持久化操作 UUID、由 UUID 派生的本地业务号、不可变来源及订单项。业务号仅为本地身份，本阶段不把它当作卡易信 `outerNumber`，不作远端幂等承诺。`procurement_operation_units` 为每个操作记录一个或多个 `(order_item_id, unit_index)`；操作提交前一次性封存单位集合。范围、来源归属、已交付单位和一个单位同时存在多个活动义务由数据库检查及部分唯一索引保护；已完成单位也不能再形成活动义务。分配数只代表本地单位，不能推导上游 `count`、倍数、价格或手续费。

操作和单位各有只追加的事件表；数据库拒绝直接伪造事件、删除历史、修改身份或清空表。操作具有递增修订，供应商订单号一旦记录不能替换或清空，`completed` 和 `rejected` 不可回退；`accepted_pending` 要求已知供应商单号。操作预留 `prepared → submit_in_flight → accepted_pending / unknown / manual_review / rejected / success_pending_finalize → completed` 等明确转移；具体合法边由数据库检查，单位有独立状态和历史。最终完成要求每个单位匹配原履约成功记录，不自行制造交付或库存流水。当前没有 worker 领取租约、发送请求、确认供应商事实或驱动这些后续状态；这些状态名称和本地约束不是协议证据。

`procurementPreparationEligibility()` 是仅供服务端事务调用的判断接口；先锁原订单与订单项，再检查来源、订单 `processing`、非零总额、足额准时支付回执、未决支付、开放对账、活动退款、退款预留和已退款事实。`allocateProcurementIdentity()` 仅在同一事务内分配本地操作及单位，不提供 HTTP 入口，不产生预算或供应商请求。两次相同单位集合的并发分配复用同一身份；部分重叠被拒绝。数据库在插入操作时重新检查付款条件。已有退款保护使用 `order_has_unresolved_fulfillment`，将未终结采购义务纳入原订单锁保护；已有外部退款事实仍遵守原记录规则。

## 锁序和事务边界

- 新订单：顾客/游客 → 原幂等 advisory 锁 → 商城策略 → 按 UUID 排序商品、SKU、数量库存及原履约配置 → 原购买资料/草稿验证；若未来存在已授权来源，再按 UUID 排序锁供应商连接、冻结模板、映射头 → 新订单和订单项 → 原购买资料及采购来源 → 库存预留 → 封存。新订单在提交前对其他事务不可见。映射管理沿用商品 → SKU → 连接 → 模板 → 映射头，来源版本最终在插入触发器复核。
- 本轮内部资格与身份分配：订单 → 订单项 → 不可变来源读取 → 采购操作 → 升序本地单位。退款沿用顾客 → 订单 → 钱包/支付尝试等原锁序；支付回执及退款 API 以订单锁与此路径串行。网络、附件完整读取与复制不持有新增事务锁。
- ⑥-4B-2 若引入会锁商品/库存/配置的准备或最终交付，须按订单 → 订单项 → 商品 → SKU → 数量库存 → 履约配置 → 按确定键排序的预算行 → 采购操作 → 单位及原履约尝试的顺序设计；预算管理不得反向获取前面的业务行。该顺序是后续接口约束，预算路径尚未实现，必须与支付 advisory 锁、退款及配置管理做真实 PostgreSQL 并发验证后才能开放发送。

## 验收和后续工作

本地专项使用独立 `_test` PostgreSQL、真实 Fastify、临时私有目录和测试进程内合成来源，验证普通 manual 订单不会因 reviewed 映射取得来源；多 SKU、不同资料和同内容合并；成交事务失败回滚；原幂等重放；映射与配置/凭据轮换后历史引用；图片原身份授权；零元、未付款、未决支付、开放对账、活动退款和退款预留；单位范围、直接 SQL 非法关系与版本、只追加历史、终态及已知单号保护。两个独立应用/数据库连接通过真实订单行锁与 `pg_blocking_pids` 门闩验证同一组单位不会产生两个操作。另分别让采购身份和退款先持有订单锁，确认等待方在提交后拒绝冲突，并验证直接 SQL 退款插入等待后由原数据库触发器拒绝；对账证据使用隔离库的合成记录，未连接真实支付服务。无替身的映射和旧 `http_json_v1` 集成测试分别检查生产选择器不会创建来源或新采购操作。原卡易信只读 API/数据库门禁与旧迁移、订单和数字履约回归使用既有测试。
