# ⑥-2C-1 正式购买填写与前后台闭环

## 范围与基线

本阶段从 ⑥-2B 验收基线 `c3a96bd6038070050c98c94b58612cab68a95b0f` 开始，把既有冻结模板、加密草稿、私有图片、购买行、统一报价、订单资料快照和独立归档附件接入商城前后台。实现仍使用现有 Nuxt 4、Vue 3、Nuxt UI 4、Fastify、PostgreSQL 与 Kysely 模块化单体。

此阶段只完成本地购买资料填写和本地订单展示。顾客填写内容不会自动成为上游采购参数；`http_json_v1` 请求、摘要、历史操作及恢复协议不变。现有六种履约方式继续由原履约系统处理，人工履约订单项可以查看购买资料；自动履约 SKU 使用填写模板时，管理端会提示资料仍需人工处理。未接入卡易信自动采购，也不改变价格、付款、退款或对外供货阶段。

## 启用状态和有效配置

前向迁移 `202610250003_purchase_form_activation_state` 移除旧 `purchase_forms_enabled` 布尔列，以 `preparing`、`active`、`paused` 表示购买填写状态。旧 `false` 安全映射为 `preparing`；旧 `true` 保留当时已启用的有效关联。迁移不修改订单摘要、已售版本、库存和资金事件。

- `preparing` 不让后台准备关联影响商城的购买行为；顾客读取有效填写模板时不暴露准备关联。
- 管理员首次启用前可检查模板冻结版本、商品默认、SKU 覆盖、配置完整性和履约处理影响；确认时提交本次影响摘要。事务锁与影响摘要校验阻止确认期间配置变化。
- 首次启用将准备关联复制到独立的 `applied_*` 关联。此后只能 `active → paused → active`，状态转换由数据库触发器和管理 API 一起约束。
- 启用后编辑关联只改准备值；管理员执行“保存并应用”后才更新生效关联。应用请求校验商品修订和准备关联内容，旧确认不能应用新编辑。
- SKU 的已应用模板覆盖优先，其次使用商品已应用模板；SKU 的 `none` 显式关闭继承，`product_default` 才继承商品规则。有效关联指向冻结版本 UUID，改动不会重写已有订单快照。
- 有模板的 SKU 暂停时不可创建新订单，即使模板字段全选填也同样处理。无模板 SKU 仍按原购买流程成交。混合购买行一并校验；报价不能绕过下单时的状态复查。
- 已提交的幂等请求先恢复原订单，再检查当前暂停状态；暂停不撤销已成交订单、履约、付款、售后、草稿或附件。
- 降级迁移在状态或关联无法由旧布尔及单层关联表达时会在 DDL 前拒绝，避免回滚暂停状态而重新放开下单、或删除准备状态。

## 草稿、附件和购买行

顾客接口只按 SKU 当前有效模板工作：读取有效模板、创建草稿、读写本人草稿、显式校验、删草稿，以及上传、查看、删除私有图片。顾客和游客 owner 由服务端会话 / 游客 cookie 推导，客户端不能指定 owner 或冻结版本。游客资料仅在登录后由原 ⑥-2B 购物车认领事务按本次指定草稿迁移归属，不扫描历史游客草稿。

草稿沿用 ⑥-2A 密文、独立 AAD、密钥环、修订冲突、限额、到期和清理约束。图片替换先校验并持久化新图，再由草稿更新及原附件删除保护协调提交；旧图容量满时仍可安全替换。更新失败时原资料和图片保留。订单成功时，成交冻结资料快照和图片归档在原订单事务中独立保存，草稿修改、过期、删除与清理不删除订单归档。

购买行继续以服务端计算的 SKU、冻结版本、规范化内容组成身份。相同 SKU 和相同规范内容合并；不同账号、选项、区服或图片维持分行。草稿、购买行、报价、订单创建继续共用 ⑥-2B v2、修订号和幂等恢复，不建立第二套购物车或订单。立即购买直接报价与成交，无需先加入购物车。编辑行时只改目标行；服务端合并时返回保留的 `lineId`；编辑失败不删除原行。

模板改版、草稿到期或修订冲突时，商品页重新取得当前 SKU 的有效模板及草稿；旧模板资料不会被静默用来成交，顾客需要在当前冻结版本下重新确认。切换 SKU 会重置字段、校验和进行中的异步状态，过期响应不能覆盖当前 SKU。填写正文不进入 URL、`sessionStorage` 或 `localStorage`。

## 订单资料的授权查看

- 顾客订单详情按订单项显示成交快照字段、成交时名称和值及对应图片。
- 游客订单沿用订单会话归属；不能通过订单 ID 猜测访问。
- 管理订单详情逐订单项展示快照和经授权读取的图片；购买资料为只读成交证据。
- 图片响应每次经过对应顾客、游客或管理员的身份及订单项授权检查，采用私有缓存、安全内容类型与响应头；不暴露存储路径、永久公网 URL 或第三方下载链接。
- 正常访问只返回授权展示所需资料，不返回数据库内部对象、密钥元数据或物理路径。含正文的草稿写入 / 校验路由采用静默请求日志；全局请求体日志也做脱敏。

## R1 精准返工记录

### 固定基线

R1 从 `c5aaf7dae76f797f334409c06e20243c1dc9bfe1` 开始。开始时本地 `HEAD`、`origin/main` 与 GitHub `main` 一致，工作区干净；未覆盖用户改动。R1 限于草稿复用、上传后保存失败、指定游客草稿认领、商品页异步状态归属、购物车绑定资料编辑五组问题及其直接回归。新增迁移为 `202610250004_cart_replacement_drafts`，此前已应用迁移没有改写。

### 问题根因、基线证据和修复

1. **商品页被动创建草稿。** 固定基线在商品页组件挂载时创建草稿，并把恢复身份保存在组件实例的 SKU 缓存；每次刷新都会失去这个缓存，连续访问会生成新的持久化空草稿，最终消耗每个主体 50 份的限额。基线浏览器复现中，51 次访问产生 20 次草稿创建请求，随后受路由限流影响。现在普通访问只读当前有效模板与恢复元数据；服务端核对 owner、有效期及冻结版本后，顾客明确选择恢复或新建。50 份限制保持不变；独立 PostgreSQL 回归验证 50 份实际不同草稿占满限额、第 51 份被拒绝但可读取已有资料。浏览器用同一游客 cookie 连续访问 51 次，创建请求为 0，之后真实创建和删除草稿成功。

2. **上传成功后保存失败堵住单图替换。** 保存修订冲突时，旧图 A 仍被密文资料引用，新上传 B 已是 `ready` 但未被引用；固定基线没有安全释放未引用 ready 附件的 HTTP 操作，B 会占满单图字段容量。真实 PostgreSQL / 临时私有目录测试证明：不释放 B 时下一张图会返回 `PURCHASE_ATTACHMENT_FIELD_LIMIT`；新 release 操作按草稿后附件锁序重新检查数据库引用表，安全释放 B 后可立即上传并保存 C。浏览器通过可控请求门闩让竞争编辑先在服务器成功、原保存收到真实 HTTP 409，再调用真实 release HTTP 并立即重试。备注特意包含 B 的完整附件 UUID，确认正文偶然出现该 ID 不会被误判为图片引用。A 的 SHA、可读性和引用在失败期间不变；上传本身故障的浏览器保护场景也保留。测试没有调用修改单图上限的路径。

3. **游客立即购买登录后缺少指定资料认领闭环。** 固定基线没有“认领本次结算明确选择的游客草稿”接口和登录回跳标记，登录后仍拿游客草稿修订请求顾客身份，无法安全完成重新报价。现在仅在单个直接购买选择显式带有 `claimGuestDraft=1` 时认领；服务端要求真实顾客会话、原游客 cookie、精确草稿 ID、owner、有效期、模板及修订都匹配，并复用单向认领事务。认领回包的新修订写入新的不透明结算选择，再重新报价；会话切换前已有的非拒绝订单 intent 阻止重新绑定或换 key。真实浏览器完成游客填写→登录→指定认领→顾客订单，重复认领返回相同修订；旧游客不能再读已认领资料或订单，未选择的游客草稿仍由原游客读取，未被批量认领。

4. **商品页异步结果归属不足。** 固定基线异步处理主要比较当前 SKU / 组件草稿，没有把每个请求启动时的草稿 ID、修订、身份代际、页面代际和操作代际作为一个不可变上下文贯穿保存、回读、校验、上传、删除及 `finally`。现在这些写回都先确认上下文仍属当前页面；页面离开会废弃代际，但不会否认已经提交到服务器的操作。真实浏览器用可控请求门闩暂停 A 的保存，在 A 收到实际 409 前切到 B 并暂停 B 的创建；释放 A 后 B 不出现错误，且 B 的忙碌提示直到 B 自己完成才消失。新增第二个门闩让 A 的真实图片上传先在服务器成功、响应留在浏览器边界时通过 SPA 切到 B；释放后 A 的附件得到安全释放响应，B 没有图片或错误污染。上传后保存冲突、私有图片替换、SKU / 商品页切换也通过真实浏览器回归。门闩负责确定调度，业务响应来自真实 API；网络不可达和浏览器进程崩溃未在本场景注入。

5. **购物车绑定草稿允许不完整写入造成延迟约束失败。** 固定基线在同一草稿内先提交不完整资料，再更新绑定修订；真实 PostgreSQL 上事务最终由购物车延迟约束拒绝，API 暴露未经处理的 500。现在编辑先进入独立 `replacement_draft`；部分内容可以持久保存而原购买行、草稿修订、内容身份和报价仍绑定上次有效资料。完整校验时在单一事务中复制仍被选择的源图片到目标草稿、保存完整加密值、合并相同内容购买行、切换目标绑定并使源草稿进入清理状态。附件行身份触发器保持不变。最终响应不确定时，按数据库引用确认副本是否已提交后再决定释放。真实 API / PostgreSQL 测试验证清空必填项、保存部分资料、恢复并完成更新；真实浏览器进一步验证原图片仍可成交归档。冲突或中止不更改旧订单快照。

## R2 独立编辑关系与附件事务收口

### 固定基线与失败证据

R2 固定基线为 `77fa655037a0b7baaa0b96cb225883a35669fa49`。开始前本地 `HEAD`、`origin/main` 和 GitHub `main` 均核对为该 SHA，工作区干净；未改写此前迁移或冻结数据。

先在该基线上加入并运行真实 PostgreSQL / HTTP 回归，得到三项失败：

1. 开始购买行 L 的独立编辑草稿 T 后，用另一份相同内容草稿追加数量；恢复 T 返回 `409 CART_REPLACEMENT_CONFLICT`。购买行数量写入触发行修订递增，但 `customer_cart_line_replacement_drafts.source_line_revision` 保持旧值。
2. 将替换关系的源草稿设为已过期、目标草稿保留有效，再运行实际清理。数据库在删除 `purchase_drafts` 时返回 `23503`，违反 `customer_cart_line_replacement_source_draft_fkey` 的 `ON DELETE RESTRICT`；reconcile 调用在该关系处中断，没有对其他候选做逐项故障隔离。
3. 用门闩暂停真实私有文件 `readVerified`，同时对同一顾客购物车执行另一笔 HTTP 资料修改。固定基线探测到该请求在 PostgreSQL 等待顾客行锁（`sawDatabaseLockWait = true`），证明复制 I/O 仍处于持锁事务范围内。

### 根因与修改

1. **购买行修订变化没有同步编辑关系。** `customer_cart_items` 的数据库触发器会在任何更新时递增 `revision`，而同内容合并路径只更新了数量。现在统一关系协调器覆盖同内容加入 / 购物车批次合并、购买行数量更新，以及编辑内容碰撞后被保留的目标行。只有购买行修订变化且原草稿 ID、原草稿修订、模板版本和内容身份全部不变时，关系才在同一事务更新 `source_line_revision` 与 `source_draft_revision`。资料、模板或绑定身份变化则在同一事务移除关系并回收未绑定的编辑草稿；目标草稿已经成为购物车有效绑定时予以保留。行删除、重新绑定、编辑碰撞、重复恢复和撤销使用同一生命周期规则。
2. **RESTRICT 外键没有对应的关系回收步骤。** 前向迁移 `202610250004_cart_replacement_drafts` 继续保留源草稿 `ON DELETE RESTRICT`，作为防止悬挂来源的数据库保护。修复后的 repair 先使过期 / 失效关系不可恢复，再处理草稿和附件：关系移除、目标草稿转为 `deleting`、目标引用解除、可安全回收的 ready / failed 附件转为 `deleting`；顾客购物车原行仍保留。正在上传的附件继续保留 reservation，直到上传完成失败或旧上传清理能证明写入已过期。清理按单个关系或草稿短事务隔离错误，删除源草稿前再次检查没有 `source_draft_id` 引用；单项失败不会回滚本批其他资源。状态转换和物理删除均可重复执行，私有文件删除幂等，进程中断留下的 `deleting` 行由后续 repair 重试。目标先过期时仅使编辑目标失效，仍有效的源草稿及购买行继续保留；源先过期时购物车原行保留，但过期资料不能再成交。路径复查还发现管理员匿名化顾客会直接删除全部购物车行；现已先按 `顾客 → 排序购买行 → 编辑关系 → 草稿 → 附件` 处理未完成编辑，再删除购物车行，避免数据库级联只删关系却留下仍占额度的活动替换草稿。
3. **附件复制处于顾客 / 购买行 / 草稿锁定事务内。** `readVerified` 和 `store` 现在在事务外完成。准备阶段只在短事务中核对会话、顾客、购买行、关系、模板、草稿修订、来源图片引用与摘要，事务提交后才读取和复制文件。最终短事务重新锁定并验证顾客、行、关系、来源与目标草稿、当前 SKU 模板、修订、有效期、图片来源 / 状态 / 存储键 / 摘要 / 容量，然后才把准备对象登记为目标附件并更新加密内容、图片引用及购物车绑定。最终事务不会依赖事务外的旧检查。对象使用原私有目录、随机附件 ID 和既有不可覆盖发布逻辑。准备失败不改有效行或已保存草稿；提交前确定失败按数据库引用检查后删除准备对象；提交确认未知时查询附件行与引用，已提交引用会被保留，未登记孤儿由原私有附件 reconciler 回收。订单归档仍使用既有独立归档存储与不可变快照。

### 锁序与验证边界

编辑关系及顾客附件清理沿用 `顾客 → 购物车行 → 编辑关系 → 按 UUID 排序的源 / 目标草稿 → 按草稿与附件 ID 排序的附件`。普通过期上传、失败附件和 ready 附件清理按 `草稿 → 附件` 逐项短事务处理。可能等待磁盘或执行物理读写的操作不持有数据库事务。清理与编辑竞争时，事务外复制完成后最终事务会再次验证关系和所有修订；冲突不会重绑旧资料。文件删除总在数据库状态先转入 `deleting` 后进行，删除确认丢失时下一轮通过状态和引用检查恢复。

## R3 提交未知保护与购物车编辑恢复

R3 固定基线为 `15bc131055d923e1a2de7f591cc8a96cef5ace82`。开始时本地 HEAD、origin/main、GitHub main 均为该 SHA，工作区干净。本轮没有数据库结构需求，没有新增或改写迁移。

### 固定基线失败证据

- 附件专项使用真实 PostgreSQL 与临时私有目录。真实复制文件后，让最终事务完成全部附件、密文与购买行写入，但在实际 COMMIT 前停住底层事务；包装器向 HTTP 路由提前报告受控确认丢失。另一连接读不到新附件行，固定基线的清理立即删除实体对象。随后门闩分别允许实际提交和实际回滚，两个参数分支都在“未确定期间对象应保留”的断言失败。这是事务仍未提交的回归，不是 R2 既有的“事务提交完成后再抛异常”用例。
- 浏览器使用基线生产构建、真实 Nuxt/API/PostgreSQL：旧编辑链接携带 `lineRevision=1, quantity=1`，另一标签同内容追加后服务端行与关系均为修订 2、数量 2。恢复页面随后真实发出的 PUT 仍带 `expectedLineRevision: 1`，返回 `409 CART_REPLACEMENT_CONFLICT`。此前一次 dev 启动等待失败和一次测试依赖解析失败仅属测试准备问题，不计作业务缺陷证据。

### 提交结果与文件回收规则

最终事务回调尚未开始或回调内校验失败时，COMMIT 没有被请求，可以按原引用检查收尾准备副本。回调已成功返回后的任何提交 / 后续响应错误均保守视为结果未知，不再以另一连接单次查不到附件行为删除依据。已成功事务也不会因为后续购物车回读失败而进入副本删除路径。

未知对象继续由原 purchase-attachments 私有对象 reconciler 回收。未登记物理对象的宽限期至少为现有 24 小时，调低草稿 / 附件行清理宽限参数不会缩短它；最终登记只接受一小时以内开始准备的副本，过时准备可安全重试。最终短事务对副本 UUID 取得非阻塞 PostgreSQL transaction advisory lock；reconciler 对单个候选取得同键的 session advisory lock，拿不到即留待后续 repair。取得后重新查询任何附件登记行，确认无登记才删除文件；不使用扫描前的 ready 行快照作删除依据。

这个对象锁只协调同一个不可覆盖 UUID 的登记和回收。文件复制继续在事务外，reconciler 的物理删除不打开 SQL 事务、不持有顾客 / 购买行 / 草稿行锁；最终登记遇到整理中的对象立即返回可重试冲突，不持有业务行锁等待文件 I/O。最终事务成功提交时登记行保护文件；最终回滚或进程退出后未登记对象在宽限期后有限地回收，不新增文件系统、配额或订单归档协议。

真实 PostgreSQL 回归包括：未提交附件行对另一连接不可见时，受控确认丢失后文件保留；将 repair 时钟推进超过 24 小时，仍在进行的事务锁阻止误删；实际提交后图片 SHA 与授权读取正确；在 ready 快照之后、文件扫描返回前提交，逐对象复查仍保护新引用；最终回滚后孤儿在宽限期后回收；重复 repair 保留已引用图片。另有回调内确定失败立即收尾副本，以及 R2 的上传复制失败、提交已完成但确认丢失、慢 I/O 不持有顾客行锁测试。
