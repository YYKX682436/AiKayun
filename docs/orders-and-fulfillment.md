# 订单与人工数字交付

阶段④-5在④-4只读结算报价上增加订单、数量库存预留、待付款订单取消/超时关闭及最小人工数字交付闭环；阶段④-6增加商品级与 SKU 级购买限制；④-7增加在线支付与异常核对；④-8在原账本上增加钱包、充值和组合支付；④-9A补齐退款申请、审核、资金预留与退款凭证；④-9B复用原现金账本增加提现审核与人工打款；⑤-1在同一订单项、库存预留/事件和履约历史上增加加密卡密池与自动发卡；⑤-2增加固定文本与固定 HTTPS 链接；⑤-3增加私有文件上传和受保护下载。三个阶段继续复用原订单项、履约尝试/交付历史、库存事件和自动交付 worker。本文件保留订单与库存规则，资金细节见[在线支付协议与运行手册](online-payments.md)、[订单退款与售后](order-refunds.md)和[提现与人工打款](withdrawals.md)。卡密池细节见[数字商品卡密池与自动发卡](digital-code-pool.md)，固定内容/链接见[固定内容与固定链接自动交付](digital-fixed-delivery.md)，私有文件见[私有文件自动交付与安全下载](digital-private-file-delivery.md)。

## 成交资格与统一报价

购物车报价、商品详情立即购买与结算预览都调用 `apps/api/src/commerce/checkout-quote.ts`。报价读取商品/SKU 状态、规格组合、当前售价、库存模式和可售库存、人工/自动交付就绪状态、游客购买策略及当前顾客自己的购买限制占用。购买限制配置公开可读；顾客历史数量只在已验证顾客报价中返回，不接受 `customerId` 查询。

可下单 SKU 必须满足：

1. 商品存在且为 `active`；SKU 启用、未退役，规格组合仍有效。
2. 库存模式为 `quantity` 或 `unlimited`。数量模式须有库存记录且可售数量足够；`code_pool` 必须使用 `quantity`，且数量库存与 SKU 卡密池状态一致。
3. 商品为数字商品，履约方式为 `manual`、`code_pool`、已明确开启的 `fixed_content`、`link` 或 `api`。人工交付要求 `manual_delivery_ready=true`；卡密池要求 `code_pool_delivery_ready=true` 且逐件预留不同卡密；固定内容/链接与外部 API 要求 `automatic_delivery_ready=true`，报价和订单快照绑定当前不可变履约版本。
4. 登录顾客会话有效；游客正价订单要求商家开启游客结算，零元订单另外要求开启免费领取。若商品或 SKU 配有账号累计或滚动 24 小时限制，游客必须登录；游客订单仍受每单限制。

## 商品与 SKU 购买限制

迁移 `202610200001_purchase_limits` 在既有 `products` 与 `product_variants` 身份上分别增加每笔订单、账号累计及滚动 24 小时三个可选上限；`NULL` 表示不限。商品每单上限为 1–4950（最多 50 个 SKU、每个 99 件），SKU 每单上限为 1–99；账号累计和滚动 24 小时上限为 1–2147483647。数据库约束与 TypeBox/API 校验共同拒绝零、负数、非整数及越界值。归档商品和永久退役 SKU 不能通过购买限制接口修改；SKU 仍必须属于路径中的商品。规则编辑走商品/SKU 现有修订号，商品编辑冲突返回 409。修改只影响新报价和新订单，不重写订单快照，也不阻止历史订单付款、关闭、退款或履约。

商品级每单规则对该商品所有所选 SKU 的数量求和；商品级累计/24 小时额度也合并该商品下全部 SKU。SKU 级规则仅统计指定 SKU。两级规则同时存在时分别检查，任一超限都拒绝；例如商品累计限购 5、SKU-A1 累计限购 2，买过 A1 两件后还可买其他 SKU 三件，但不能再买 A1。

额度以既有订单及不可变订单项为事实来源，不维护可任意加减的购买计数器。一个订单项数量只求和一次；支付回执和履约记录用 `EXISTS` 分类订单，不与订单项做可能放大数量的 JOIN。计入规则为：

- `pending_payment`、`processing`、`completed` 当前订单计入；历史状态事件曾进入 `processing` 或 `completed` 也计入。
- 安全取消/超时关闭的未付款订单释放额度。只有在没有已进入处理/完成的状态历史、未终态支付尝试、支付回执、未解决资金义务、进行中退款、进行中/未知/成功履约尝试或实际交付时，关闭才足以证明订单从未成交。失败、明确取消或过期的终态支付尝试本身不占额度。
- 已确认支付、迟到/异常收款或存在任何支付回执的订单，即使后来全额退款或被关闭，仍计入账号累计历史；退款不改订单原数量与成交快照。实际交付或履约事实也永久保留购买历史。
- 尚未解决或含糊的资金/支付/履约状态采用保守计入，避免关闭状态掩盖迟到付款或交付。必须由现有支付、退款或对账流程解决异常；本阶段不自动判断异常资金应返还购买额度。
- 滚动 24 小时以数据库生成的新订单 `created_at` 为基准，窗口为严格晚于该时间减去 24 小时；恰好位于边界的历史订单不计入。结算预览使用数据库查询时钟展示当前额度，订单封存触发器则以该订单真实 `created_at` 再次验证。客户端时间不参与计算。

商品和 SKU 公开配置随目录响应返回；顾客累计数量和剩余额度只随本人结算报价返回。购物车本身不占额度，但已创建且未安全关闭的订单会占用。登录后报价按商品聚合多 SKU 数量，并取单次上限与各自可用累计/滚动额度中的最小值。任何配置/库存/价格/购买额度变化都会改变报价 token；订单事务再用同一服务重新报价。

报价仅用于顾客确认。下单请求提交规范化 SKU/数量、幂等键和报价摘要 `quoteToken`，不接受前端提供的售价、商品名、顾客 ID、库存或金额。摘要用于发现预览之后的变化；服务端仍在成交事务内重新计算全部报价。价格、库存、商品状态、规格、履约就绪或购买资格变化时，返回 `409` 与新的报价，要求页面显示并让顾客再次提交。

## 下单事务、锁顺序和库存

`POST /api/v1/checkout/orders` 的事务按以下顺序处理：

1. 登录顾客先以 `FOR UPDATE` 锁定并重新验证顾客行，再以 `FOR SHARE` 验证当前会话；这把同账号的跨设备购买串行化，也避免先取得共享锁后升级写锁的死锁。游客则锁定当前游客订单会话。游客令牌只从安全 Cookie 读取，数据库只存令牌摘要。
2. 对“身份类型 + 身份 ID + 幂等键”取得 PostgreSQL 事务级 advisory lock；在锁目录和库存前检查已有订单。相同键和相同规范化 SKU/数量返回原订单而不新建订单或额度占用；相同键、不同内容返回 `ORDER_IDEMPOTENCY_CONFLICT`。
3. 共享锁定店铺策略行，重新验证游客开关和超时时间。
4. 按商品 UUID 顺序取得商品行 `FOR SHARE`，再按商品 UUID、SKU UUID 顺序锁 SKU `FOR UPDATE`。
5. 按商品 UUID、SKU UUID 顺序锁数量库存行 `FOR UPDATE`，最后按 SKU 顺序共享锁定履约配置。
6. 使用与④-4报价相同的核心逻辑在事务内重算价格、库存、顾客购买量和所有商品/SKU 限制；确认报价摘要未变后插入订单和成交快照、插入数量库存预留、封存订单项并返回订单详情。数据库在订单项封存时独立重算限购，作为绕过 API 的最后一道约束。

所有顾客订单插入触发器还会原子递增该顾客独立的 `purchase_limit_lock_version` 写入围栏；它不是购买计数器。直接使用 `REPEATABLE READ` 的并发 SQL 事务若在等待顾客锁前已读取旧快照，PostgreSQL 会以 `40001` 中止第二个写入，避免旧快照绕过配额。游客不能配置账号累计规则，所以无需顾客额度序列化。目录锁顺序仍为商品 `FOR SHARE` → SKU `FOR UPDATE` → 数量库存 `FOR UPDATE` → 履约 `FOR SHARE`；SKU 限购修改先锁定/验证所属商品，再锁该商品内 SKU。不存在 SKU 锁后才不稳定竞争多个商品额度锁的路径。

单笔事务只允许最多 50 个 SKU，每 SKU 数量 1～99。SKU 在写入前排序并合并重复项。遇到 PostgreSQL `40001` 或 `40P01` 最多重试 3 次；重试后仍冲突时返回 `ORDER_CONCURRENT_CONFLICT`。任何插入、快照、库存事件或封存失败都会回滚整笔订单。

订单项快照保存成交商品名、商品类型、SKU 码、规格、成交单价、数量、行金额、库存模式、履约方式和（固定内容/链接订单的）私有版本引用；订单保存金额、币种、身份、幂等摘要和原始到期时间。公开 SKU 快照不包含私有正文。之后的商品改价、履约内容编辑、暂停销售、下架、SKU 退役或策略调整不会改写已有快照。

数量库存通过现有 `order_inventory_reservations` 和 `order_inventory_events` 写入。订单创建只插入预留记录，由④-1事件触发器实际更新 `reserved` 并递增 SKU 库存修订号；应用代码不直接写 `reserved`。`unlimited` 不创建数量预留；`resource_pool`、`external` 未具备供应能力，拒绝下单。商品与 SKU 锁顺序与③阶段库存调整、SKU 退役及④-1库存事件一致。

顾客取消、超时 worker 和数据库状态触发器共用 `order_has_unresolved_payment_attempts(order_id)`。订单关闭持有订单行后取得按订单 UUID 哈希的 PostgreSQL 事务级 advisory lock，再读取支付/资金义务。支付尝试 `UPDATE` 在 PostgreSQL 已锁尝试行后取得同一 advisory lock；订单关闭的 `AFTER` 触发器因此不得再更新支付尝试行。支付尝试 `INSERT` 不取 advisory lock，由冻结的④-1校验触发器先锁订单行并验证订单仍可支付。回执路径按订单行→支付尝试行→状态更新 advisory lock 执行。这样取消、超时、支付状态变化和回执按订单行串行，且不会出现订单关闭持有 advisory 后反向等待尝试行的闭环。

新建的外部订单支付尝试必须在 `INSERT` 时带未来 `expires_at`。冻结的④-1结构仍允许旧记录期限为 `NULL`；这类 `created/pending` 记录始终按未决支付保护。写入后期限不可单独修改；唯一例外是在同一受保护更新中执行 `created → pending` 并写入新期限。数据库先校验该期限为未来值，再取得订单 advisory lock 并确认订单仍待付款且未超时。该规则也禁止在订单关闭后修改尝试期限，以及修改终态尝试期限。支付状态语义如下：

| 支付尝试状态 | 订单关闭规则 |
| --- | --- |
| `created` | 可能已向第三方发起请求；`expires_at` 为 `NULL` 或仍在未来时阻止关闭。不能把 `created` 当作尚未发起支付的证明。 |
| `pending` | 等待第三方确认；有效期为 `NULL` 或仍在未来时阻止关闭。所有新 `pending` 必须有未来 `expires_at` 且期限不可变。旧的 `pending + NULL` 记录仍被视为未决，不会因迁移而被错误关闭。 |
| `failed`、`cancelled`、`expired` | 终态可解除支付尝试阻断；若有组合钱包冻结，状态触发器须先记录唯一解冻流水，冻结未解决时仍禁止关闭。仍需通过未退款实收、退款预留、活动退款及履约义务检查。安全到期只说明本次尝试期限已过，不证明第三方没有实际收款。 |
| `succeeded`、`late_succeeded`、`reconciliation_required` | 缺少回执时按未决状态阻止关闭；有回执时逐笔检查实收和成功退款。未退款收款、异常收款或退款处理中仍阻止关闭。 |

进入 `pending` 时数据库要求订单仍处于待付款且订单期限尚未结束。顾客取消、超时 worker 和直接 SQL 更新均受数据库 guard 最终保护。期限不可变规则使订单关闭读取的期限与创建/状态转换时确认的期限一致，不存在 `created → created` 期限更新绕过订单 advisory lock 的路径。安全过期不会自动把第三方尝试改成 `cancelled`：关闭保留原尝试和回执关联，之后的实际收款仍可写入并被分类为迟到/异常。订单关闭触发器写入状态历史并通过库存事件释放未交付预留；重复关闭不会重复释放。组合钱包冻结是独立未结资金义务，即使外部尝试已过期也会阻止关闭；只有失败、明确取消或已处理的异常结果触发④-1解冻后才能关闭。

第三方回执和订单关闭在 PostgreSQL 订单行锁上串行。迟到回执始终保留原金额、通道凭证和 `late`/异常分类，不会把订单重新打开或变成已付款履约订单。若订单过期但仍有 `created/pending` 的 NULL 或未来期限尝试，回执处理不会先关闭订单；收款按订单/尝试期限分类，随后必须走退款或对账边界。

## 订单超时

`storefront_customer_policy.unpaid_order_timeout_minutes` 默认 15 分钟；后台只允许设置 5、15 或 30 分钟。④-1订单创建触发器把当时策略写入订单的 `unpaid_expires_at`，以后修改店铺设置不会改变既有订单。

API 启动时立即执行一次未付款订单清理，然后每 60 秒执行一轮，每轮最多领取 100 个可关闭订单。PostgreSQL 使用 `FOR UPDATE SKIP LOCKED` 在多个实例间分配任务；服务重启后立即恢复过期任务。worker、取消接口、回执触发的过期判定和订单 guard 共用未决支付函数；worker 在选取批次时先排除未决支付、未结资金/退款和处理中履约，受保护订单不会占满批次而饿死后续订单。

## 游客会话与顾客访问

`POST /api/v1/guest/session` 会自动建立或恢复游客会话，不返回令牌。Cookie 为 HttpOnly、SameSite=Lax，并按部署配置启用 Secure；令牌为高熵随机值，数据库仅存摘要。会话到期后，历史订单继续留存，但旧会话不能再读取或取消它们。

顾客订单始终从已验证登录会话取得 `customer_id`。游客订单始终从安全 Cookie 对应的 `guest_order_session_id` 取得。登录顾客不能切换到游客订单 API；游客也不能读取顾客订单或其他游客会话的订单。详情越权统一返回 404，订单 API 设置 `Cache-Control: no-store`。页面请求在顾客身份版本变化后丢弃旧响应，不将旧身份订单写入当前视图。

## 人工数字交付、卡密池、固定内容和外部 API 自动交付

迁移 `202610190004_orders` 增加 `product_variant_fulfillment.manual_delivery_ready`，默认 `false`；⑤-1迁移 `202610210002_code_pool` 为同一配置增加 `code_pool_delivery_ready`，默认 `false`。商家必须在商品 SKU 管理页明确开启所需资格。人工数字交付可用于数量或不限数量库存；卡密池只能用于启用且未退役的数字商品 `quantity` SKU。未配置或未就绪的履约方式持续拒绝新报价。

管理员在 `/admin/orders/:id` 为订单项逐件录入真实内容。`POST /api/v1/admin/orders/:id/items/:itemId/fulfillments` 需要管理员权限、同源 Origin 和双提交 CSRF。服务和数据库都要求订单为 `processing`：零元订单由④-1订单创建触发器直接置为此状态；正价订单只有④-1确认真实、足额、按时收款后才能进入此状态。本阶段没有任何管理员标记付款成功的接口。

每次履约创建④-1 `order_item_fulfillment_attempts`，记录数量、操作身份、操作幂等键和结果摘要；交付正文存入新增的私有 `order_item_fulfillment_deliveries`，一件商品一条记录，包含操作身份、单件 SHA-256 和时间。只有履约尝试成功后，④-1触发器才更新已交付数量、消耗数量库存，并在全部订单项完成时把订单置为 `completed`。相同操作键与内容重放返回原结果；相同键对应不同内容返回冲突。

人工交付内容行数必须等于此次交付数量，每件最多 512 个字符。卡密池在下单时通过库存预留事件逐件绑定不同卡密；确认交付时写入相同 `order_item_fulfillment_attempts` 与 `order_item_fulfillment_deliveries`，成功触发原订单库存消费及订单完成。人工内容只允许管理员录入；卡密内容在服务端解密后只返回给订单所属顾客、有效游客订单会话或管理员，响应禁止缓存。数据库拒绝修改、删除或截断历史交付内容；退款不重置交付、库存或卡密状态。应用日志不记录请求正文、Cookie、会话令牌或卡密明文。

人工录入、卡密池自动发货、固定文本/固定链接、私有文件和外部 API 自动交付都保存在原订单履约历史。卡密池逐件消耗 quantity 库存；固定内容、文件和 API 可重复售卖，但 quantity SKU 成功交付时仍消费该订单已有数量预留；unlimited SKU 不创建数量预留或库存事件。自动交付订单项在下单事务中绑定报价版本；同一数字交付调度器处理自动履约，失败重试不会影响已确认的支付回执。文件交付每个单位只记录不可变版本引用；顾客下载时对真实订单、已付款事实、成功履约及顾客/游客会话逐次授权，并在支持单一 Range 响应前校验完整文件 SHA-256。卡密池预检查、批次、状态、撤回和密钥运维见[数字商品卡密池与自动发卡](digital-code-pool.md)；固定内容/链接版本、安全 Markdown、AES-GCM 密钥轮换、对账拦截与恢复见[固定内容与固定链接自动交付](digital-fixed-delivery.md)；文件存储、下载和备份见[私有文件自动交付与安全下载](digital-private-file-delivery.md)；供应商配置、`http_json_v1` 协议、凭据保护、外部操作状态及未知恢复见[外部 API 自动发货](external-api-delivery.md)。

## 退款及订单售后

④-9A 的售后状态与订单履约状态、支付尝试状态分开保存。顾客可以申请全额或部分退款；后台显示真实回执、来源分配、预留/已退金额及操作历史。订单的 `order_financial_status` 和顾客状态投影按已确认回执与退款分配推导“部分已退款/已全额退款”，不会把 `processing` 或 `completed` 改写为退款状态。

批准的顾客退款在一个 PostgreSQL 事务内按实收来源分配并写入既有钱包账本：赠送退赠送、现金退现金、支付宝/微信等外部实收退本人现金钱包。退款分配使用已有 `operation_id`、`wallet_operations`、`wallet_ledger_entries` 和回执退款累计字段，不直接改余额。审计、分配、回执与钱包流水任一写入失败都会回滚。

游客没有钱包，只允许将外部收款分配到原支付来源的人工处理流程。系统不调用未验收的 ZPAY 自动退款接口；转账结果未知时继续预留，失败才可释放重试，实际转账后须录入退款流水号、确切金额、时间和证据摘要才确认成功。

退款不清除成交/交付历史，不恢复已消费库存、不重复释放已释放库存，也不减少购买限额统计。开放支付对账、异常回执、未决支付或履约进行中/结果未知时，退款与订单关闭继续受数据库保护。退款、人工尝试、账本和状态审计规则见[订单退款与售后](order-refunds.md)。

## 数据库变更与阶段边界

新增安全迁移 `202610190004_orders`：新增 SKU 就绪标记、履约管理员身份字段和私有交付内容表；替换订单关闭保护与库存关闭触发器实现，统一未决支付、未解决钱包冻结、退款、实际收款及履约阻断规则，并避免关闭触发器反向更新支付尝试。支付期限契约限定新尝试的初始期限，并阻止订单关闭并发期间单独改期限。④-1订单表、库存预留、库存事件、支付回执、履约尝试和订单状态事件均继续复用。回滚迁移会拒绝删除已有交付内容。
