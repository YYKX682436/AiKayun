# 订单退款与售后（④-9A）

④-9A在④-1既有退款申请、资金来源分配、支付回执、钱包操作、不可变账本和财务投影上补齐顾客申请、商家审核、退款预留、退款确认、人工游客原路退款及审计。不新增第二套余额或退款账本；提现留在④-9B。

## 资金边界

可退款金额只来自本订单的 `payment_receipts`。可用收款必须关联状态为 `succeeded` 或 `late_succeeded`、回执分类为 `on_time` 或 `late` 的支付尝试。金额不符、超额、尚未确认的尝试、回调待查及其他异常事实不视为可退款余额；出现未决支付、`reconciliation_required` 或开放 `payment_provider_reconciliation_cases` 时，申请和处理均被阻止。

每张回执的额度按 `amount - refunded_amount - refund_reserved_amount` 计算。已有活动申请中尚未分配的金额也占用订单可申请额度。申请触发器锁订单并检查总额，随后数据库分配触发器锁订单、退款记录、回执，原子增加回执预留额；同一回执上的预留额与已退款额始终不能超过该回执实收。所有资金以两位小数的 `NUMERIC(18,2)` 保存。

| 收款来源 | 顾客订单退款去向 | 账本效果 |
| --- | --- | --- |
| 赠送钱包 (`gift`) | 顾客本人 `gift_balance` | 通过该分配唯一 `operation_id` 写 `wallet_operations` 和 `wallet_ledger_entries.credit_available`，桶为 `gift` |
| 现金钱包 (`cash`) | 顾客本人 `cash_balance` | 同上，桶为 `cash` |
| 支付宝/微信等外部 (`external`) | 顾客本人 `cash_balance` | 外部收款退款不假称原路到账；通过原有钱包退款账本退到顾客现金余额 |
| 游客外部收款 | 仅原外部来源的人工退款 | 不创建顾客钱包操作；须记录人工处理和真实转账结果 |

组合支付的订单会同时保留赠送、现金、外部多张回执，每笔分配引用单一原回执，分别按上表退回。赠送资金不能变成现金。API 不接受退款顾客 ID；顾客身份来自登录会话，游客身份来自订单会话 Cookie。

## 状态与申请流程

退款请求独立于订单履约状态。主要状态为 `requested → approved → processing → succeeded`；游客退款在部分操作完成时可为 `partially_succeeded`。审核拒绝记为 `cancelled` 并保留原因。人工原路退款明确失败会释放该分配，退款可进入 `failed` 并由管理员重新预留；实际成功与未知状态均保留可审计处理记录。失败或结果未知不会被显示成成功。

每笔分配只可从 `reserved` 转移一次到 `succeeded` 或 `released`。顾客钱包退款的审核批准、分配预留、账本入账、收款回执更新、退款完成状态和审计均在同一个 PostgreSQL 事务中完成；任一步失败即整笔回滚。幂等重放返回已有申请或操作结果，不另建分配和流水。两位管理员审核同一申请时，订单与退款行锁及状态条件只允许一方成功。

顾客前台显示确认实收、当前可申请、已退款和预留金额，区分“部分已退款”与“已全额退款”，显示申请原因、审核状态、资金来源、去向、分配及操作进度。全额/部分结果来自财务事实，不把订单的 `pending_payment`、`processing`、`completed` 或 `closed` 履约状态改写为退款状态。`order_financial_status` 汇总已收及已退事实；顾客状态投影据此展示已退款或部分退款。

退款不删除订单、支付回执、交付或账本历史，不恢复已消费库存，不再次释放已取消订单库存，也不减少限购购买历史。已交付订单仍保留完成状态和交付凭证。只有原订单关闭规则本身允许关闭时，未交付订单才可关闭；履约进行中或未知结果仍阻止关闭。部分退款不使仍有未退实收的订单满足全额退款关闭条件。

## 游客人工原路退款

游客无钱包，系统不提供把游客收款转给某个顾客的方式，也不把订单号当成资金认领证明。当前 ZPAY 接入没有经本阶段验收的自动退款协议；服务不会请求或臆造 ZPAY 退款 API。

审核通过后，外部来源金额先以 `destination='original_source'` 预留。管理员必须先记录开始处理的操作，再在线下经支付渠道办理原路退款。未核清时可记为 `unknown`，预留继续占用，禁止重复启动活动中的同一分配；确认没有实际转账才可记为 `failed` 并释放。只有实际转账已经完成，管理员录入真实退款流水号、精确金额、实际时间和证据摘要后，数据库才允许将分配记为成功并增加回执 `refunded_amount`。金额必须与预留分配完全相等。管理员、启动/确认时间、结果摘要和状态变化保留在只追加的审计记录中。

系统把外部人工转账与数据库事务明确分开：外部操作前先持久化人工尝试，绝不持有数据库行锁等待银行或支付平台。实际退款发生后若 API 响应丢失，管理员应查询原操作并复核同一结果，不能再次转账。若转账结果未知，保留 `unknown` 与预留，并先人工核实既有流水；只有明确未转账的失败结果才能释放后重试。

人工证据摘要是管理员核对结果的审计文本，不是支付服务商自动验真凭证或证据文件存储。系统不声称自动验证外部资金退回。

## 并发、事务锁序与对账

退款事务遵守已有顾客、订单、钱包、支付顺序：

1. 顾客发起申请时先验证并锁定顾客及当前会话，再锁订单；登录顾客退款继续锁本人钱包账户，再按 UUID 顺序锁订单的支付尝试，最后按回执时间、来源桶和 UUID 顺序锁实收回执。
2. 管理员审核/处理先按订单归属锁顾客（若订单属于顾客），再锁订单、顾客钱包（若有）、支付尝试（按 UUID）、退款申请和回执。游客订单没有顾客/钱包锁。
3. 退款分配触发器在订单 → 退款 → 回执顺序再次核验来源归属、桶和额度。现有回执/钱包触发器再通过分配唯一操作 ID 写入退款账本。
4. 服务商回调沿用④-7锁序：顾客（组合支付时）→订单→钱包（组合支付时）→支付尝试→服务商交易号 advisory lock→回执。因此同一订单上的支付回执与退款申请/审核在订单行串行；退款按锁后最新回执重算可退款金额。
5. 钱包账户行锁与钱包消费、充值和结算共享④-8锁序。退款账本在与钱包支付相同的钱包账户锁下增加可用余额，不能出现负数；顾客钱包支出只由已有钱包付款流水执行。

退款代码不持有数据库锁执行外部网络操作。状态和凭证在一个事务内写入；审计事件、退款分配、钱包操作和账本均不可修改/删除。数据库拒绝直接改钱包余额，拒绝赠送资金转桶、拒绝游客钱包去向、拒绝跨订单分配及拒绝异常回执上的退款入账。开放对账案例和未决支付不会被管理员审核绕过。

## API 与页面

| 方法与路径 | 用途 | 保护 |
| --- | --- | --- |
| `GET /api/v1/customer/orders/:id/refunds` | 顾客读取本人订单退款汇总与历史 | 顾客会话、订单归属、`no-store` |
| `POST /api/v1/customer/orders/:id/refunds` | 顾客申请本人订单退款 | 顾客会话、Origin、双提交 CSRF、限流、幂等键 |
| `GET /api/v1/guest/orders/:id/refunds` | 当前游客会话读取退款汇总 | 游客会话 Cookie、订单归属、`no-store` |
| `POST /api/v1/guest/orders/:id/refunds` | 游客申请人工原路退款 | 游客会话 Cookie、Origin、双提交 CSRF、限流、幂等键 |
| `GET /api/v1/admin/orders/:id/refunds` | 查看订单退款、回执、资金去向、操作与审计 | 管理员会话、`no-store` |
| `POST /api/v1/admin/orders/:id/refunds/:refundId/approve` | 审核通过并按真实资金来源分配预留；顾客退款同事务入账 | 管理员会话、Origin、CSRF、幂等键 |
| `POST /api/v1/admin/orders/:id/refunds/:refundId/reject` | 拒绝申请并保存理由 | 管理员会话、Origin、CSRF、幂等键 |
| `POST /api/v1/admin/orders/:id/refunds/:refundId/retry` | 为已释放游客退款金额重新预留来源 | 管理员会话、Origin、CSRF、幂等键 |
| `POST /api/v1/admin/orders/:id/refunds/:refundId/allocations/:allocationId/manual-attempts` | 持久化游客人工转账开始记录 | 管理员会话、Origin、CSRF、幂等键 |
| `POST /api/v1/admin/orders/:id/refunds/:refundId/allocations/:allocationId/manual-attempts/:attemptId/resolve` | 记录游客退款成功、失败或结果未知 | 管理员会话、Origin、CSRF、真实结果字段及幂等键 |

顾客流程位于 `/orders/:id`，后台审核位于 `/admin/orders/:id`，复用 Nuxt UI、现有语义设计令牌及深浅色主题，响应式适配移动端和桌面端。页面在 SSR 下按已验证身份读取订单；退款详情使用 `no-store`。退款区清楚显示游客人工原路处理说明，不展示自动退款承诺。

## 迁移与 PostgreSQL 验收

迁移 `202610200005_refunds` 仅向前新增退款原因、审核者、只追加审计表和游客人工尝试表，扩充原退款保护触发器及状态校验。它不修改 `202610180001_trade_foundation` 等冻结历史迁移，也不建立第二套退款账本。既有 `order_refunds`、`order_refund_allocations`、`payment_receipts`、`wallet_operations`、`wallet_ledger_entries`、`order_financial_status`、库存事件和订单状态事件继续作为资金/履约事实。

集成测试在真实 PostgreSQL 18 `_test` 数据库中运行事务、触发器和确定性并发测试。覆盖现金、赠送、外部与组合支付来源，全额和累计部分退款，幂等重放、并发审核、余额/账本一致、赠送分桶、人工游客成功/未知/失败释放与重试、游客钱包防护、CSRF、开放对账拦截、回调并发，以及履约/库存/限购历史保留。真实商户资金转账仍需相应支付渠道人工核验；自动退款 API 和④-9B提现不属于本阶段。
