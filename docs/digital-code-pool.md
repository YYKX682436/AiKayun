# 数字商品卡密池与自动发卡

⑤-1为每个数字商品 SKU 增加独立、加密、可审计的卡密池。卡密复用现有订单、订单项、`order_inventory_reservations`、`order_inventory_events`、`order_item_fulfillment_attempts` 和 `order_item_fulfillment_deliveries`；没有第二套卡密订单或库存流水，也不修改阶段④冻结迁移。实现由前向迁移 `202610210002_code_pool` 开始。

## 数据和状态

`code_pool_batches` 保留每次导入或撤回的请求摘要、摘要密钥 ID、请求/接受/重复/无效数量、管理员和时间；`code_pool_entries` 保存 SKU、导入批次、密文、加密 nonce/tag、密钥 ID、HMAC 内容指纹和状态。批次、卡密身份、密文和已交付历史由数据库约束保护，不允许更新、删除或截断。前向迁移 `202610210003_code_pool_operation_key` 只增加摘要密钥 ID，不改写历史 `request_sha256`；没有该 ID 的旧批次会用密钥环中保留的每个密钥验证原摘要。

| 卡密状态 | 含义 | 可进行的状态变更 |
| --- | --- | --- |
| `staged` | 仅存在于尚未提交的导入事务 | 同一库存事件提交为 `available` |
| `available` | 未售可用；对应 SKU 可售库存 | 下单预留为 `reserved`，或经确认安全撤回为 `revoked` |
| `reserved` | 已由订单项独占；不会被其他 SKU/订单分配 | 安全关闭订单后回到 `available`；履约成功后变为 `delivered` |
| `delivered` | 已成功交付的永久凭证历史 | 终态，不因取消、退款或重试重新入池 |
| `revoked` | 管理员撤回的未售卡密 | 终态，保留原导入批次和撤回批次关联 |

数据库约束确保同一 SKU 内每个 HMAC 指纹只入库一次；交付记录对卡密条目唯一。跨 SKU 可重复使用相同字符串，但不会互相抢占。每件商品默认一条卡密，数量为 N 的订单项预留并交付 N 条不同卡密。

## 加密与密钥管理

`CODE_POOL_ENCRYPTION_KEY_RING` 是独立于支付凭证的服务端密钥环，例如：

```json
{"activeKeyId":"2026-10","keys":{"2026-10":"<base64-encoded-32-random-bytes>"}}
```

为每个部署环境生成独立随机 32 字节密钥；可用 `openssl rand -base64 32` 生成。生产密钥应放在部署平台的 Secret/密钥管理系统，不提交 `.env`、Compose 文件、数据库、备份旁车文件或日志。不要复用 Compose/E2E 固定测试密钥。

卡密明文使用 Node.js `aes-256-gcm` 加密，12 字节随机 nonce，保存认证 tag；AAD 绑定 SKU/卡密条目或订单项/交付 ID/卡密条目，避免密文跨记录替换。密文使用 UTF-8 原文加密，导入不会 trim、改变大小写或折叠内部空格。HMAC-SHA-256 的用途密钥由密钥环密钥通过带用途标签的 HMAC 分离：分别用于 SKU 内重复指纹、幂等请求摘要和交付摘要。数据库与 API 不保存可逆 Base64 明文。

轮换时新增 `activeKeyId` 并保留 `keys` 中所有仍被历史记录引用的旧密钥。卡密及其交付记录是不可变的，旧密钥必须在数据库备份、恢复、迁移、灾备及密钥轮换期间保留；删除被历史条目引用的密钥会阻止读取该卡密，也会阻止该 SKU 新导入/开售。轮换完成前验证所有历史 `encryption_key_id` 与 `fingerprint_key_id` 仍存在。密钥缺失时系统关闭相关动作并在履约尝试中留下 `CODE_POOL_KEY_UNAVAILABLE`，不能退化成明文或伪成功。

安全轮换顺序：先把新旧完整密钥环分发到所有 API 实例，保持旧 `activeKeyId`，确认每个实例都能读取新旧密钥；再切换各实例的活动密钥。禁止在有实例缺少新密钥时先让其他实例用新密钥写入。批次按保存的 `request_fingerprint_key_id` 验证摘要；新旧活动密钥实例只要都保留该密钥，就能并发重放同一操作。SKU 卡密指纹继续针对密钥环全部保留密钥预检，确保新旧活动密钥实例之间仍能识别重复内容。旧密钥须保留至所有引用它的卡密、交付和批次历史都不再需要读取。

## 库存原子一致性

卡密池 SKU 必须配置 `quantity` 库存。其核心不变量为：

```text
quantity_inventory.stocked = available 卡密数 + reserved 卡密数
quantity_inventory.reserved = reserved 卡密数
可售 quantity = stocked - reserved = available 卡密数
```

已交付卡密不再属于库存；库存消费事件将它从 `reserved` 转为 `delivered` 并递减 `stocked`、`reserved`。导入与撤回分别由 `restock`、`withdraw` 事件改变库存和卡密状态。下单预留、订单安全取消释放、履约成功消费，仍使用既有订单库存预留及 `reserve`、`release`、`consume` 事件。每条池批次与该批次数量事件由延迟数据库约束核对。

导入前必须先将 SKU 配置为 `quantity`，并用现有库存调整将旧数量清零；设置卡密池后，普通数量调整、数量模式切换和删除库存记录都不能绕过卡密事件。只有 `available` 条目可以撤回，撤回需要管理员输入原因并明确确认 `REVOKE_UNSOLD_CODES`。订单已预留/交付卡密不允许撤回。归档商品会保留库存及卡密事实；商品复制会生成新 SKU，不复制库存、履约资格、批次或卡密。永久退役 SKU 不可启用新销售，其既有订单/卡密事实保持可追踪。

## 锁顺序与事务边界

下单继续采用既有次序：顾客或游客会话 → 事务级幂等 advisory lock → 店铺策略 → 按 UUID 排序的商品 → 按商品/SKU 排序的 SKU → 数量库存 → 履约配置。订单项封存、库存预留记录与预留事件同一事务提交；库存事件触发器先锁 SKU 和数量库存，再以 `FOR UPDATE SKIP LOCKED` 选取可用卡密。选取数量不足会回滚整个下单事务，不会创建部分卡密预留。

后台导入/撤回与销售资格修改先锁商品、SKU、数量库存，再处理池条目和对应库存事件。它们与下单争用同一 SKU/库存锁，因此与最后一条卡密并发时只会有一种完整结果：下单成功且撤回冲突，或撤回成功且报价/下单冲突。

自动履约按订单 → 订单项 → 商品 → SKU → 数量库存 → 履约配置 → 已预留卡密锁定。回调、取消、人工履约及自动履约都先串行化同一订单；数据库也拒绝未进入 `processing`、金额未实际确认、存在未决支付/开放对账或无一条有效密文记录对应一个单位的卡密成功尝试。支付回执和订单状态在原事务写入，自动发卡失败不会回滚或丢失已确认收款凭证。

## 自动发货、重试与恢复

API 启动时立即运行 PostgreSQL worker，之后每秒轮询，每轮最多领取 20 个订单项。worker 使用 `FOR UPDATE SKIP LOCKED` 锁订单，多实例可以并行处理不同订单；同一订单不会被重复交付。对每个订单项，在一个短数据库事务中验证订单/收款、卡密/库存账实、将已有履约尝试置为处理中、写入加密交付记录并将尝试置为成功。原数据库触发器随后将预留库存记为消耗，转移卡密状态，并在全部订单项完成时完成订单。

服务仅在 PostgreSQL 执行，不依赖 Redis 或消息队列。事务中途进程退出会整体回滚，订单的卡密仍保持原预留事实；数据库已经提交但 API 响应丢失时，订单/交付历史就是幂等结果，后续读取不会重新分配卡密。可恢复的失败会写入原履约尝试并记录原因及 `retry_after`，以 1 秒起始、指数退避、最长 5 分钟的有界重试恢复；数据库异常若导致主事务回滚，会在独立事务中尽量补记失败尝试。尝试状态不会被伪造为成功。

常见自动失败代码：

| 代码 | 排查方向 |
| --- | --- |
| `CODE_POOL_DATA_INCONSISTENT` | 核对订单预留、卡密状态和 `order_inventory_events`；不要直接改库存数或卡密状态。 |
| `CODE_POOL_KEY_UNAVAILABLE` | 恢复对应历史密钥，检查部署 Secret 是否包含全部密钥 ID。 |
| `CODE_POOL_DECRYPTION_FAILED` | 检查密文认证、备份完整性和密钥是否配对；禁止重新生成或覆盖原卡密。 |
| `CODE_POOL_PAYMENT_UNRESOLVED` | 在既有支付/对账流程确认足额实收并关闭未决情况；不能用管理操作直接放行发货。 |

## 权限与隐私

- 订单 `pending_payment` 时订单详情只返回空交付数组；卡密只在原履约尝试成功后可见。
- 顾客订单读取使用当前登录账户归属检查；游客订单读取使用 HttpOnly 游客会话归属检查；其他顾客/游客无法读取，管理员按现有后台权限查看。
- API 在服务端完成身份和订单归属验证后才解密卡密。响应设置 `Cache-Control: private, no-store`；商品详情、公开目录、SEO/sitemap 和公共 SSR 数据不包含卡密。
- 预检查只返回行号、重复/无效原因和计数；后台条目、批次、订单列表和失败详情不返回未售卡密全文。卡密内容不写入日志、错误响应、请求摘要或审计批注。
- 顾客订单详情支持多件卡密展示和逐条复制。后台 SKU 编辑页支持粘贴、UTF-8 TXT、单列 CSV、预检查、批次/状态管理和明确撤回；订单详情显示自动履约尝试、失败原因及重试时间。
- 同一操作标识重放时，服务端必须验证原 `request_sha256`：新批次使用其保存的密钥 ID；旧批次依次用所有仍保留的密钥验证。摘要无法验证时返回冲突或明确的历史密钥错误，绝不因卡密已存在或已撤回而跳过摘要校验。

## 验证与操作

⑤-1 的真实 PostgreSQL 集成测试覆盖同批/跨批重复、不同 SKU 隔离、最后一条卡密并发下单、撤回/预留并发、多件交付、同订单重试、多 worker、零元订单、足额付款回执、付款未完成不可读、安全取消释放、退款后不回池、库存事件账实、复制/归档/退役保护、顾客/游客/管理员访问以及缺密钥恢复。浏览器测试通过实际后台 SKU 页面导入，完成顾客结算和订单详情读取/复制，并检查公开 SSR 不包含卡密。

```sh
pnpm verify
```

必须将 `TEST_DATABASE_URL` 指向名称以 `_test` 结尾的专用 PostgreSQL 数据库；E2E 需要独立测试媒体目录和浏览器。验证结束后检查 Compose 项目、测试数据库和临时媒体目录，只清理本次创建的测试资源。生产部署、生产迁移和密钥初始化不属于本阶段本地验收。
