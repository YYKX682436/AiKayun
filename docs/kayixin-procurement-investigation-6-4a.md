# ⑥-4A：卡易信 V3 采购协议调查与架构方案

调查日期：2026-10-27。固定代码基线：`2090f75d70fe4349a25a9849d62759ea6dd0fe8f`。本文件是方案，不是采购实现或采购授权。本轮不更改生产代码、数据库、部署或连接资格，不发送可扣款请求、不创建采购订单。

## 证据口径与放行结论

- **源码事实**：固定基线中的实现和数据库约束；证明本商城当前行为，不证明上游商户行为。
- **官方协议原文**：本轮通过文档正常密码访问，逐页读取卡易信《商家客户 API 3.0》；仅证明文档声明，不证明具体商户站点实际实现或扣费行为。
- **历史文档记载**：仓库此前记录的实验，单独标注日期与范围。
- **隔离夹具**：本地或历史受控测试，证明所测实现及场景，不证明真实卡易信商户履行相同协议。
- **真实商户证据**：须绑定目标站点、接口版本、配置及证据日期，并经授权核验；本轮无真实采购证据。
- **NOT_VERIFIED**：缺少足以支撑该项的协议原文或目标商户授权证据；不按相似平台、示例字段名或 HTTP 状态猜测。

结论：**保持卡易信仅只读、`procurementReady=false`、`fulfillmentEligible=false`，不得作为旧 `http_json_v1` 可销售来源。当前不能安全启用真实采购，也不能据负查单或相同业务号推断可重购。** 本报告中的采购状态和存储关系是未来设计，以下正式架构决策与门禁作为后续实现约束；不得把本地设计当作供应商承诺。⑥-4B 仅允许实现隔离执行内核，不建设可向真实卡易信扣费的可用采购通道，继续保留现有只读及数据库禁售约束。

## 固定基线的调用链和数据来源

1. 管理员连接页 → `admin-supplier-connections.ts`：认证及 CSRF、当前不可变连接配置/凭据版本、解密 → `kayixin-customer-v3.ts` 三个固定只读操作 → `supplier-http.ts` 出站 → 返回前复核当前配置；只读测试只记 `catalog_read_v3`。本地检查入口为 `apps/api/src/catalog/admin-supplier-connections.ts:126`、`:355`、`:503`。账户、列表和详情固定路径及签名见 [⑥-1](supplier-kayixin-v3-readonly.md) 和 `apps/api/src/commerce/kayixin-customer-v3.ts:12`、`:213`。
2. 管理员商品映射 → 同一商品详情只读入口，HTTP 在事务外 → 观察（含配置版本和结构指纹）→ 本地 SKU 对应映射头 → 校验字段路径、选项、必填项与结构 → 追加不可变 reviewed 版本。模板、配置、SKU 或上游结构漂移会要求重审。映射锁序为商品 → SKU → 供应商连接 → 冻结模板 → 映射头；参见 `apps/api/src/catalog/admin-supplier-product-mappings.ts:172`、`:891`、`:1025` 和 [⑥-2C-2](purchase-product-mappings-6-2c-2.md)。预览只产生合成中间表示，不是上游请求体。
3. 顾客/游客填写 → 受身份绑定的加密草稿、私有图片 → 以 SKU、模板及内容身份区分的购买行 → 统一报价与原订单幂等检查 → 成交事务冻结订单和订单项资料；图片先在事务外校验/复制，再绑定独立归档。资料使用订单项专用加密上下文，按订单授权读取，不回读可变草稿；`apps/api/src/commerce/purchase-order-attachments.ts:91`、`:167`、`:275`，以及 [⑥-2B](purchase-lines-6-2b.md)、[⑥-2C-1](purchase-forms-6-2c-1.md)。当前订单快照尚不自动包含未来采购来源；未来采用供应商自动采购履约的新订单必须在成交事务内冻结该来源，不能默认为当前已实现。
4. 现有订单 → 原支付回执和对账 → 原退款/库存/履约。六种履约方式为 `manual`、`code_pool`、`fixed_content`、`link`、`file`、`api`；成功后复用原逐单位交付和库存事件。现有 `api` 仅是 `http_json_v1`，并非卡易信采购：单件操作 → 事务内持久身份与租约 → 事务外创建或查单 → 安全保存结果 → 原交付事务。详见 `apps/api/src/commerce/code-pool-delivery-worker.ts:840`、`:945`、`:1090`、`:1260`、`:1339`、`:1516` 和 [⑤-4](external-api-delivery.md)、[⑤-5](digital-fulfillment-acceptance.md)。
5. `apps/api/src/db/migrations/202610240001_kayixin_readonly.ts:47` 的数据库约束/触发器与 API 门禁一起禁止卡易信启用旧销售资格、绑定旧 API 履约或插入旧供应商操作。只读成功不提供采购资格；连接协议固定，配置和凭据版本独立保存，历史凭据通过限制性引用及协议专用 AES-256-GCM AAD 保留，轮换密钥须保留历史解密能力。参见 `apps/api/src/commerce/supplier-api-crypto.ts:82` 和 [⑥-1](supplier-kayixin-v3-readonly.md)。

现有固定只读调用将最终 UTF-8 JSON 字符串原样用于签名和传输；按本轮复核的官方签名规则签名为 `MD5(AppID + AppSecret + "3.0" + timestamp + bodyJson)`，带 `X-APP-ID`、`X-Version`、`X-Timestamp`、`X-Signature`。账户为空正文。基础地址限制为 HTTPS 站点根；DNS 全答案检查与地址固定、TLS 校验、禁止重定向、总超时及有界字节传输在 `apps/api/src/commerce/supplier-http.ts:107`。上游内容不可信，不能执行上游脚本或正则，也不能把响应、顾客资料、凭据或签名原文写入日志。仓库对只读成功解析 `code=1000` 的实现不证明采购成功规则。

## 可复用能力和必须新增的边界

可复用现有订单、支付回执、对账、退款、库存事件、逐单位交付与审计，不新建一套交易账本；复用付款/退款与履约的订单锁、不可变订单资料及私有附件、审核映射版本、连接/密钥版本与安全传输原语。复用现有持久操作、短事务、租约、结果加密、失败退避和 SIGKILL 测试模式，但不是把旧协议行为视为卡易信保证。原有 `http_json_v1` 使用商城成交 `unit_price` 填 `unitAmount`（`code-pool-delivery-worker.ts:883`、`:1299`）；这不是卡易信采购金额。

须独立设计卡易信协议适配、协议版本与语义分类、严格类型及身份校验、上游采购事实、资料编码/图片处理、独立采购资格、预算和核账。写接口应有明确固定操作与最小权限，不能将只读端点扩展为任意路径代理。具体字段、请求和成功规则待证据确认；原有数据库禁止绑定卡易信到旧操作的保护在本轮保持。

## 提议的采购身份与状态

**正式决策：成交冻结采购来源。** 未来采用供应商自动采购履约的新订单，在成交事务内冻结供应商连接、配置/凭据版本、审核映射版本及结构指纹、上游商品/SKU 身份、冻结模板及购买资料身份，并关联订单资料和附件来源。成交后的映射或配置变化不得静默改变原采购来源。未持有来源快照的历史订单不得直接自动绑定当前映射；当前基线尚未实现这一采购来源快照，不能把既有订单资料快照视为已经具备它。

**正式决策：本地单位与上游操作分层。** 本地 `orderItemId + unitIndex` 继续负责逐单位交付唯一性；每个上游采购操作拥有持久 UUID 和稳定的本地业务身份，可覆盖经过验证的多个本地单位，但必须保存确定性分配及各单位的部分完成关系。数据库须防止同一单位出现多个活动采购义务、重复交付或并发重复创建，约束身份、状态、租约和结果一致性，并保留只追加的历史。数量、倍数和扣费单位未经验证前，不构造真实采购数量，也不假设本地单位与上游请求一对一。

建议分离以下采购事实与原履约尝试，不把采购成功等同于已交付：

| 提议状态 | 进入条件及后续 |
| --- | --- |
| `prepared` | 订单确认付款、无未决支付/对账/退款冲突；锁内核实所有版本、资格与预算并持久化稳定身份。用户要求确认付款；现有零元订单履约例外不自动授权采购，零元/全优惠须另决。 |
| `submit_in_flight` | 先短事务领取租约、持久记请求意图和预算占用；提交后事务外发送。崩溃后不能推断请求未发出。 |
| `accepted_pending` | 仅在有效证据确认供应商已接单时记录供应商单号及加密证据，继续按原身份查单；不是交付完成。 |
| `unknown` | 发送后超时、断线、5xx、含义不明、响应解析/持久化失败或崩溃等无法证明结果时保留身份、已知单号及预算；只查原操作或转人工，不能新建号重购。 |
| `rejected` | 只有经目标协议证实明确未执行、未扣费且无后续履约义务的拒绝才进入；重试是否可新操作需显式授权和业务规则。可重试的本地故障仅在能证明请求未发出时继续原操作；否则按未知。 |
| `manual_review` | 单号冲突、已知单号查不到、身份/金额不符、负查单证明不足、长时间未知、上游状态 9 或历史凭据不可用；保留原事实、预算和退款保护，人工核对有审计。 |
| `success_pending_finalize` | 仅在经协议验证的业务结果确认成功后，先持久化加密结果、身份和必要扣费事实；不能因交付事务失败重复采购。 |
| `completed` | 原订单锁内再次核实资金/退款资格、身份及单位唯一性，原交付事务幂等写入逐单位交付/库存事件后完成。部分结果仅按证实的单位处理，未确认部分继续保留义务。 |

上游明确接受、处理中、实际履约完成、部分成功和上游退款必须分别映射为有证据的状态；上游状态 9 保留原始状态、人工核对，不自动完成交付或退款。以上只是本地语义，不能编造 V3 状态枚举。查单始终绑定原始身份和已知供应商单号；不同上游 ID、金额或其他关键身份冲突进入人工核对。不得用当前配置或当前商品资料替换历史版本，供应商撤销旧凭据导致无法查单时人工处置，不自动换新凭据重购。

## 锁、恢复、预算与资金竞争

- 保持现有交付锁序：订单 → 订单项 → 商品 → SKU → 数量库存 → 配置 → 供应商操作 → 尝试；预算行及采购操作的新增锁位置须在⑥-4B与下单、映射、退款、预算管理的所有路径一起建立一致全局顺序，按确定顺序锁多单位。任何网络、文件读取、图片上传均在事务外；重入短事务重新检查身份、资格、租约及版本。真实 PostgreSQL 并发屏障和数据库约束共同验证，不能仅靠应用检查。
- 租约 token / 代际用于防止旧 worker 覆盖新状态；**租约不约束供应商扣费**。过期后不能因一次负查单或旧 worker 不再持租约就重发。迟到响应可作为受保护、只追加的证据，保留已知供应商单号并核查归属；权威状态更新须检查租约/身份，冲突转人工，不丢弃已知身份。证据持久化本身也可能因 SIGKILL 失败，必须仍依原身份恢复。
- **正式决策：预算分离每日新增额度与全局未核销风险。** 采购预算独立于商城售价、人工成本和供应商参考报价，包含供应商/SKU 开关、单笔限额、每日新增额度、全局未核销风险限额及紧急暂停；在同一短事务原子预留最大风险额，并处理并发、日切、部分扣费、实际核销及审计。结果未知或扣费未核实的义务跨天继续占用全局未核销风险额度，日切不能释放或重置该义务；释放仅凭充分证据。币种、最大扣费和手续费规则未经过确认时不得开放自动采购。真实费用上限必须由已核实的供应商服务端价格约束及手续费规则支持；本地预算不能保证上游不会超扣。暂停阻止新发送，仍允许安全查单、保存迟到事实和人工对账；不能抹掉已有义务。
- 订单必须已确认付款且没有未决支付、退款预留/活动退款、已退款或开放对账冲突，资格在建操作与最终交付时均复核。采购已发或结果未知时沿原资金保护阻止新退款动作；退款先取得资格则禁止新采购和新交付。若外部退款凭证或采购扣费已发生，保存事实并对账，不能为了满足状态机抹掉事实；冲突交人工处理。参见 [⑤-5](digital-fulfillment-acceptance.md) 第 40、56 行。
- 已确认上游成功须先可靠持久化密文，再最终交付；提交结果未知时保留对象和证据，不用单次读不到证明回滚。数据库、历史密钥和私有卷须一致备份恢复；新购买资料归档的真实 SIGKILL 及在线生产一致备份当前仍 **NOT_VERIFIED**。

## 三类最高风险场景

1. **重复扣款**：供应商执行后响应丢失或租约过期，第二 worker 新号重购。对策：持久单位身份、无新号、未知保留、原身份查单；当前 `outerNumber` 去重未证明，不允许自动重发；只有未来真实站点证明幂等范围、有效期限及足够强的一致性条件，并经另行审核，才能重新设计重发规则。仅凭数据库锁或本地 token 无法保证远端至多扣一次。
2. **已扣款但查不到**：读副本延迟、单号保存失败、密钥轮换或对方查单范围差异均可能产生负结果。对策：保留原业务号、已知上游 ID、加密证据、预算及退款保护，按经验证的查询渠道核查，不能把负结果视为无采购；必要时人工与商户账单核账。
3. **退款与交付竞争**：付款后网络采购在途时退款或上游成功后本地交付。对策：订单锁内双向资格保护，未知采购阻止新退款，退款先取得资格则停止新采购和新交付；上游已发生的扣费、交付或退款始终先安全保存，人工协调，不制造第二笔采购或抹去资金事实。

## ⑥-4B 实现建议与测试清单

⑥-4B **仅允许实现隔离执行内核**，包括面向隔离夹具的持久身份、状态、预算、恢复及并发验证；暂不建设可以向真实卡易信扣费的可用采购通道，不打开真实购买权限。保持现有卡易信只读门禁、数据库禁售约束、旧 `http_json_v1` 语义及历史迁移。真实协议未确定的字段及商户语义只留明确阻断，不构造真实采购载荷或数量。成交冻结来源、单位与上游操作分层以及历史订单禁自动绑定按本报告正式决策执行；新增锁序与确定性分配细节仍需实现前评审。不得追填顾客资料。

建议验证：

- 真实 PostgreSQL 的唯一约束、不可变版本/身份、非法状态和直接 SQL 绕过、锁序及并发预算；支付未决、开放对账、退款在途/完成和零元订单全部阻止新采购。
- 独立受控 HTTP 夹具：请求前后强杀、提交后响应丢失、超时/5xx、接受但未交付、重复/部分结果、业务码未知、恶意/畸形/超大响应、身份/价格/ID 冲突、限流、凭据轮换、历史密钥缺失、TLS/DNS/重定向、敏感值回显；夹具只能证明隔离内核行为，不能证明真实商户结果、扣费或售后事实。
- 双 worker 及租约过期、旧响应迟到、查单负结果、已知 ID 消失、人工核对和重复人工操作；验证无新业务号、无重复扣费请求或交付、单号不丢、预算不提前释放。当前卡易信隔离内核须断言不自动重发；未来若另经审核修改此门禁，相关重发断言只能适用已证明的商户幂等契约。
- 独立真实进程 `SIGKILL`：操作/预算提交后 HTTP 前、上游执行后响应前、响应解析后本地提交前、成功结果提交后交付前、最终交付提交后；重启核对操作身份、原始支付/退款事实、供应商夹具执行数、单位交付/库存与预算。覆盖购买资料归档及图片准备的独立强杀边界，不沿用⑤-5证据代替。
- 退款与提交/查单/结果保存/最终交付的真实数据库屏障竞争；预算跨并发 worker/日切/暂停，实际扣款超限及未知占额；旧协议、六种履约、历史凭据、附件授权与敏感日志回归。
- 隔离数据库、密钥环、公开及私有文件的同一时间点备份/恢复，核查历史订单、采购身份、密文、附件摘要、预算和对账；生产恢复须单独实测，不能以夹具证明。

## 逐级放行与正式商户联调最小条件

所有条件逐级完成、记录证据和负责人，前一层不能替代后一层：

1. 获取并核对真实站点、版本、原始协议与字段语义，关闭矩阵中阻断项；明确各操作权限和授权。
2. 在无真实扣款的隔离夹具中完成采购身份、状态、约束、并发、预算与退款保护验收。
3. 真实进程 SIGKILL 与恢复逐边界通过，账实和逐单位交付一致。
4. 获得明确、单独授权后，以隔离商户和明确低额上限进行小额实测；本轮没有此授权，也不执行。
5. 逐项核对真实扣费、费用与币种、查单一致性、重复号/幂等、异步结果及最终交付，发现不符即暂停。
6. 供应商及 SKU 独立开关、单笔/每日新增预算、全局未核销风险限额、并发原子预留和紧急暂停均已验证，并具备人工核对和值班响应。
7. 部署数据库、全部历史密钥和私有文件一致备份与恢复完成并演练；确认旧凭据失效或密钥缺失处置。
8. 所有证据及剩余风险经方案审核后，才可以另行决定开启真实自动采购。

最小联调条件还包括：确定目标 HTTPS 商户和软件/API 版本、接口原文与书面语义、受限商户账户及专用低余额、通过安全配置注入的凭据（不入聊天/仓库/日志）、测试商品及事先批准的金额/次数/时间、可核验账单及上游订单、独立测试顾客资料、人工负责人及停止机制。只读认证通过不能替代采购授权与上述门禁。
