# ⑦-4：运维与运行健康管理

商城冻结起点为 `63bc8bdea0c2d31b22eb2b4ab32e6d471183c56b`，授权中心只读基线为 `185dac80204f60abbaa63ffeb5af7d7054b685d7`。本阶段不部署生产、不调用真实商户接口，也不修改授权中心。

## 健康与诊断

`live` 仅表示 API 进程能响应；`ready` 检查数据库、完整已编译迁移名与执行记录、部分核心列，以及媒体和私有文件根目录的可访问性。探针有时间上限，不访问支付或授权中心，也不进行大文件 SHA 扫描。迁移记录与核心列检查不能证明每个物理 schema 对象完好。授权失效、撤销或中心失联不直接决定健康；新经营准入仍由原有授权门禁决定，历史义务继续使用原业务状态机。

管理员运维页区分经营授权和历史义务依赖。独立诊断检查存储目录、实例身份、Trust Store 和 Pending Key 文件可访问性，核对数据库中历史支付与交付 key ID 是否存在于配置；文件存在或 key ID 存在并不证明完整性、绑定或能解密，不能证明时显示未知。文件一致性结果和原业务页面仍须结合判断。所有详细 API 使用既有管理员会话；只读导出仅包含聚合与白名单诊断，不包含原始业务记录或秘密文件。

## Worker 与业务风险

四类观察分别覆盖未付款到期、本地数字交付、上游交付恢复及授权续签。PostgreSQL 保存最近扫描、成功和失败时间与固定失败码，进程每类每分钟最多一个周期观察和两次状态切换；写入失败不会阻塞业务状态机。多实例共用每类一行，表示至少一个实例最近完成扫描，不能证明所有实例均正常。未付款及交付观察超过 3 分钟、授权观察超过 70 分钟视为未知；扫描正常且积压为零表示空闲，不等于 Worker 停止。未配置发行信任配置显示未知，未取得续签锁的实例不冒充扫描成功。本地扫描的积压包括尚未创建上游 operation 的 API 交付；上游积压仅计算已建立 operation 的到期动作。

支付请求及人工退款、打款未决超过 10 分钟需人工核对，连续未决超过 30 分钟升级严重程度。支付 `requesting` 和 `unknown` 使用不可变的请求开始时间计算持续未决时间；进入 `unknown` 的确切时间无法从现有支付状态证明，页面不把请求起点伪装成状态转换时间。退款与提现同样标注操作开始后的未决时长。对账案例、已终结支付遗留冻结、提现不确定、交付失败/未知、超过 24 小时的交付积压、上游人工核对和授权续签重试按数据库真实状态展示。正常待付款、正常审核及合理冻结不自动当作事故。可证明的时间展示最早时间及持续时间，否则显示未知；人工响应目标是开始核对的时间，不能当作已经解决的 SLA。不得手工标记支付成功、强制解冻或对可能已成功的外部请求直接重发；沿用认证查单、审计与提现确认。

## 文件检查与回收

检查与修复分离，默认不执行修复或自动删除。执行节点上运行 `docker compose exec -T api /nodejs/bin/node dist/media/operations-file-check-cli.js`，四类依次只读检查；跨进程锁避免并发，同一数据库六小时内最多一次，进程最长五分钟，未完成或超过七天的结果显示未知。媒体和私有文件沿用现有身份、引用与 SHA 校验；草稿和订单附件最多各校验前 1000 个，超限显示未知，当前没有分页续扫。结果只反映最后执行节点的挂载，多个不同存储节点需要分别安排检查并人工保留结果。

现有 `--repair` 可能改变业务状态或缺少可证明的并发删除保护，因此未作为定时任务，四类均不自动回收。未来若实现自动回收，必须逐类证明至少 24 小时宽限、删除前重新确认所有有效和历史引用、锁与状态转换，以及并发、断连和未知提交时的安全性。历史引用文件缺失、损坏或无法解密只报告并从可信备份恢复，不自动替换或重建。

## 日志与保留

API 只记录路由模板、请求 ID、方法、状态、耗时和固定错误码；不记录 query、请求体、Cookie、授权头或原始异常。Nuxt BFF 对代理异常和未处理错误使用固定安全响应与日志，Caddy 错误日志过滤 URI、请求头和客户端地址；默认不启用访问日志。生产 Compose 使用 Docker `json-file` 有界轮转，每文件 10 MiB、保留 5 个文件。正式环境不注册 `/api/docs`，开发和测试仍可使用。诊断导出不包含日志原文、数据库行或秘密文件。
